## 1) 학습 목표

- 작업 완료 보고에 포함해야 할 핵심 정보를 설명할 수 있다.
- 인수인계 시 전달해야 할 맥락 정보를 구분할 수 있다.
- 진행 상황 보고와 완료 보고의 차이를 설명할 수 있다.
- 보고의 품질이 팀 생산성에 미치는 영향을 이해할 수 있다.

## 2) 업무 맥락

개발 작업은 코드를 작성하면 끝이 아니다. 완료한 것을 정확히 보고하고, 필요 시 후임자에게 인수인계하는 것까지가 하나의 태스크다. 보고가 불충분하면 매니저가 진행 상황을 정확히 파악할 수 없고, 인수인계가 불완전하면 후임자가 같은 조사를 처음부터 다시 하게 된다. 보고와 인수인계 능력은 기술력과 동등하게 평가되는 직장 기초 스킬이다.

## 3) 핵심 설명

### 완료 보고에 포함할 정보

작업 완료 보고에는 다음 5가지 정보를 포함해야 한다.

**1. 무엇을 완료했는가(What)**
- 태스크 명칭과 이슈 번호
- 구현한 기능의 개요

**2. 어떻게 구현했는가(How)**
- 기술적 접근 방식의 요약
- 변경한 파일이나 영향 범위

**3. 테스트 결과(Verification)**
- 동작 확인 방법과 결과
- 테스트 케이스 커버리지

**4. 남은 과제·제한 사항(Remaining)**
- 이번에 대응하지 않은 항목과 그 이유
- 알려진 제한 사항이나 리스크

**5. 참고 정보(References)**
- 관련 PR 링크
- 참고한 문서나 이슈

### 진행 보고와 완료 보고의 차이

| 항목 | 진행 보고 | 완료 보고 |
|------|-----------|-----------|
| 타이밍 | 작업 중 (일간/주간) | 작업 완료 시 |
| 주요 내용 | 무엇을 했는가, 다음에 무엇을 할 것인가, 블로커는 무엇인가 | 무엇을 완료했는가, 어떻게 테스트했는가, 남은 과제는 무엇인가 |
| 목적 | 계획과의 차이 조기 발견 | 결과물 확인과 다음 공정으로의 전환 |

진행 보고에서 중요한 것은 "예정과 실적의 차이"와 "블로커(방해 요소)"의 공유다. 문제를 빨리 공유하면 팀으로서 빨리 대처할 수 있다.

### 인수인계 문서에 포함할 정보

인수인계 문서는 후임자가 "왜 이렇게 되어 있는가"를 이해하기 위해 쓴다. 코드만으로는 전달되지 않는 맥락을 남기는 것이 목적이다.

**1. 배경과 경위**
- 왜 이 태스크가 필요했는가
- 도중에 변경된 요건이나 방침

**2. 아키텍처 판단**
- 기술 선택의 이유 ("A가 아닌 B를 선택한 이유")
- 트레이드오프 설명

**3. 운영상 주의점**
- 정기적으로 확인해야 할 항목
- 발생할 수 있는 문제와 대처법

**4. 관련 리소스**
- 관련 코드, 설정 파일, 문서의 경로
- 담당자 연락처 (질문이 있을 경우)

### 좋은 보고의 원칙

- **사실과 추측을 분리한다**: "테스트는 통과했다(사실). 성능 영향은 경미할 것으로 보인다(추측)."
- **간결하게 쓴다**: 긴 문장보다 글머리 기호로 요점을 전달한다.
- **읽는 사람의 관점에서 쓴다**: 자신이 알고 있는 것을 전제로 하지 않는다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 완료 보고: "로그인 기능 수정했습니다. 확인 부탁드립니다."
- 문제점:
  - 무엇을 수정했는지 구체적이지 않다.
  - 어떻게 확인하면 되는지 알 수 없다.
  - 영향 범위나 남은 과제 기재가 없다.
- 개선 예:
  - 대응 내용: 로그인 화면에서 이메일 주소의 대소문자를 구분하지 않도록 수정 (PR #456)
  - 테스트: `test@Example.com`과 `test@example.com`으로 동일 사용자로 로그인 가능 확인
  - 영향 범위: 로그인 처리만. 회원가입에는 영향 없음
  - 남은 과제: 기존 사용자의 이메일 주소가 대소문자 혼재인 경우의 데이터 마이그레이션은 미대응 (이슈 #789에서 별도 대응 예정)

### 시나리오 B
- 상황: 3개월간 담당했던 기능을 다른 개발자에게 인수인계한다.
- 인수인계 문서 구성:
  - 기능 개요와 배경 (왜 만들었는가, 누가 사용하는가)
  - 아키텍처 다이어그램 (주요 컴포넌트와 데이터 흐름)
  - 기술 판단 기록 ("라이브러리 X가 아닌 Y를 사용한 이유: X는 유지보수가 중단되었으므로")
  - 알려진 과제 목록 (성능 개선이 필요한 부분, 향후 대응 예정 이슈)
  - 운영 절차 (배포 방법, 로그 확인 위치, 장애 시 대응 플로)
  - 질문 연락처

## 5) 자주 하는 실수

1. "했습니다"만 쓰고 구체적 내용을 적지 않는다.
읽는 사람이 무엇을 확인해야 하는지 몰라 추가 질문이 발생한다.

2. 남은 과제나 제한 사항을 보고하지 않는다.
나중에 문제가 발견되어 "왜 보고하지 않았느냐"며 신뢰를 잃는다.

3. 인수인계 문서에 코드 설명만 쓰고 배경을 쓰지 않는다.
후임자가 코드는 읽을 수 있지만 "왜 이렇게 되어 있는지"를 몰라 잘못된 변경을 하게 된다.

4. 진행 보고에서 블로커를 공유하지 않는다.
혼자 안고 있다가 스케줄 지연이 직전까지 발각되지 않는다.

5. 사실과 추측을 섞어 쓴다.
추측이 사실로 전달되어 잘못된 판단의 근거가 된다.

## 6) 확인 질문

1. 완료 보고에 포함해야 할 5가지 정보는 무엇인가?
2. 진행 보고와 완료 보고의 목적 차이는 무엇인가?
3. 인수인계 문서에서 가장 중요한 "코드만으로 전달되지 않는 정보"란 무엇인가?
4. 보고에서 사실과 추측을 분리해야 하는 이유는 무엇인가?
5. 진행 보고에서 블로커를 조기에 공유해야 하는 이유는 무엇인가?

## 7) 문항 발췌 메모

- 사실형 후보: 완료 보고의 필수 요소, 진행 보고와 완료 보고의 차이
- 판단형 후보: 불충분한 보고의 개선점 지적
- 시나리오형 후보: 모호한 완료 보고 개선, 인수인계 문서 구성 판단
- 오답 유도 포인트: 남은 과제 생략, 사실과 추측 혼동
