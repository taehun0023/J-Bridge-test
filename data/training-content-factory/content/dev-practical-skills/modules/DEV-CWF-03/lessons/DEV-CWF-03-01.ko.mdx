## 1) 학습 목표

- 이슈의 제목과 설명에서 작업 범위를 정확히 파악할 수 있다.
- 우선순위 라벨(Priority / Severity)의 의미를 읽을 수 있다.
- 이슈와 풀 리퀘스트(PR)의 관계를 설명할 수 있다.
- 라벨, 마일스톤, 담당자 정보를 조합해 태스크의 위치를 판단할 수 있다.

## 2) 업무 맥락

팀 개발에서는 구두 지시뿐 아니라 이슈 트래커(Jira, GitHub Issues, Backlog 등)를 통해 태스크가 관리된다. 신입 개발자가 처음 부딪히는 과제 중 하나는 "이 이슈에서 내가 무엇을 어디까지 해야 하는가"를 정확히 읽어내는 것이다. 이슈 내용을 올바르게 해석하지 못하면 작업 범위를 초과하거나 부족한 구현을 하게 되어 재작업이 발생한다. 이 능력은 실제로 코드를 작성하기 전 단계에서 필요한 기초 스킬이다.

## 3) 핵심 설명

### 이슈의 구조

일반적인 이슈에는 다음 요소가 포함된다.

- **제목**: 작업 내용의 요약. "OO 화면에 XX 기능을 추가한다"처럼 대상과 동작이 명시된 것이 좋은 이슈다.
- **설명(Description)**: 배경, 목적, 수락 조건(Acceptance Criteria)이 기술된다. 수락 조건이 있으면 그것이 작업의 완료 기준이 된다.
- **라벨(Labels)**: `bug`, `feature`, `enhancement`, `documentation` 등 종류 라벨과, `P0`~`P3`이나 `critical`, `low` 등 우선도 라벨이 붙는다.
- **마일스톤 / 스프린트**: 해당 이슈가 언제까지 완료되어야 하는지의 기한 정보.
- **담당자(Assignee)**: 담당자. 자신에게 할당된 이슈는 자신의 책임 범위다.

### 우선순위 읽는 법

많은 프로젝트에서는 우선순위를 다음과 같이 분류한다.

| 라벨 | 의미 | 대응 속도 |
|------|------|-----------|
| P0 / Critical | 서비스 중단·데이터 손실 수준 | 즉시 대응 |
| P1 / High | 주요 기능에 영향, 우회 가능 | 당일~익일 |
| P2 / Medium | 개선 필요하나 긴급하지 않음 | 스프린트 내 |
| P3 / Low | 있으면 좋은 개선 | 백로그 |

Severity는 "영향의 크기"를, Priority는 "언제 대응할 것인가"를 나타낸다. 둘 다 붙어 있을 때는 Priority가 작업 순서의 판단 기준이 된다.

### 이슈와 PR의 관계

이슈는 "무엇을 해야 하는가"를 정의하고, PR은 "어떻게 구현했는가"를 보여준다. 일반적인 흐름은 다음과 같다.

1. 이슈가 생성된다 (요구 정의)
2. 브랜치를 생성하여 구현한다
3. PR을 생성하고 이슈 번호를 참조한다 (`Closes #123`)
4. 리뷰·머지 후 이슈가 자동으로 닫힌다

하나의 이슈에 여러 PR이 만들어질 수 있다. 반대로, PR이 어떤 이슈에도 연결되어 있지 않으면 작업 추적이 어려워진다.

### 작업 범위 파악

이슈 설명에 수락 조건이 명시되어 있으면 그 조건을 충족하는 것이 "완료"의 정의다. 조건이 모호한 경우에는 작업을 시작하기 전에 확인해야 한다. "아마 이런 뜻이겠지"라고 추측해서 진행하면 기대와 다른 결과물이 나올 위험이 있다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 이슈 제목: "사용자 목록 화면 표시 수정"
- 라벨: `bug`, `P1`
- 설명: "사용자 목록 화면에서 이름이 긴 경우 레이아웃이 깨진다."
- 수락 조건: 없음
- 해석:
  - "레이아웃이 깨진다"의 구체적 기준이 불명확하다. 어떤 화면 폭에서, 몇 글자부터 깨지는지 알 수 없다.
  - P1이므로 당일~익일 대응이 기대된다.
  - 작업 시작 전에 깨짐의 재현 조건과 수정 후 기대값을 담당자에게 확인해야 한다.

### 시나리오 B
- 이슈 제목: "주문 확인 메일에 취소 링크 추가"
- 라벨: `feature`, `P2`
- 설명: "주문 확인 메일 본문 끝에 주문 취소용 링크를 추가한다. 링크는 주문 후 24시간 이내에만 유효하다."
- 수락 조건:
  1. 메일 본문에 취소 링크가 표시된다
  2. 링크는 주문으로부터 24시간 이내에만 작동한다
  3. 24시간 초과 시 에러 페이지를 표시한다
- 해석:
  - 수락 조건이 3개 명시되어 있어 작업 범위가 명확하다.
  - P2이므로 스프린트 내 대응이면 된다.
  - 메일 템플릿 변경과 취소 API의 유효기간 체크, 두 가지 작업이 필요하다고 추측할 수 있다.

## 5) 자주 하는 실수

1. 제목만 읽고 설명을 읽지 않은 채 작업을 시작한다.
수락 조건이나 배경 정보를 놓치고 의도와 다른 구현을 하게 된다.

2. 우선순위 라벨을 무시하고 백로그 순서대로 작업한다.
P0/P1 이슈가 방치되어 서비스 영향이 길어진다.

3. 수락 조건이 모호한 상태에서 스스로 판단해 구현을 진행한다.
나중에 "그런 의미가 아니었다"며 재작업이 발생한다.

4. 이슈와 PR을 연결하지 않고 PR을 만든다.
작업 추적이 불가능해지고 나중에 "이 PR은 왜 만든 것인가"를 알 수 없게 된다.

5. 하나의 PR에서 여러 이슈를 한꺼번에 처리한다.
리뷰가 복잡해지고 머지 판단이 어려워진다.

## 6) 확인 질문

1. 이슈 설명에서 가장 중요한 요소는 무엇인가?
2. Priority와 Severity의 차이는 무엇인가?
3. 수락 조건이 없는 이슈에 대해 가장 먼저 해야 할 일은 무엇인가?
4. `Closes #123`이라는 PR 기술은 무엇을 의미하는가?
5. P0 라벨이 붙은 이슈를 발견했을 때 어떻게 대응해야 하는가?

## 7) 문항 발췌 메모

- 사실형 후보: 이슈의 구성 요소, 우선순위 라벨의 의미
- 판단형 후보: 수락 조건이 모호할 때의 대응 판단
- 시나리오형 후보: 불완전한 이슈를 읽고 부족한 정보 지적하기
- 오답 유도 포인트: Severity와 Priority 혼동, 제목만으로 작업 범위 판단
