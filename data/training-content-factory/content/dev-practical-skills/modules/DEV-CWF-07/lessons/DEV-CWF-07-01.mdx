## 1) 学習目標

- 技術ドキュメントの種類と各々の目的を説明できる。
- ドキュメントから必要な情報を素早く見つける戦略を説明できる。
- ドキュメントが古い、または不完全な場合の対処方法を説明できる。
- 公式ドキュメントとコミュニティ資料の使い分けを判断できる。

## 2) 業務コンテキスト

開発者の業務時間の大きな部分は、コードを書くことではなくドキュメントを読むことに費やされる。新しいライブラリの導入、APIの統合、フレームワークのバージョンアップなど、あらゆる場面でドキュメントを参照する必要がある。しかし、ドキュメントの量は膨大であり、すべてを頭から読む時間はない。「必要な情報を最短時間で見つける」能力は、開発速度に直結する実務スキルである。

## 3) 要点解説

### 技術ドキュメントの種類

| 種類 | 目的 | 例 |
|------|------|-----|
| README | プロジェクトの概要、セットアップ手順 | GitHubリポジトリのREADME.md |
| APIリファレンス | エンドポイント、パラメータ、レスポンスの仕様 | Swagger / OpenAPI |
| チュートリアル | 手順に沿って学ぶ入門ガイド | Getting Started |
| ガイド（How-to） | 特定のタスクの実現方法 | 認証の実装方法 |
| コンセプト解説 | 設計思想や仕組みの説明 | アーキテクチャ概要 |
| 変更履歴（Changelog） | バージョンごとの変更内容 | CHANGELOG.md |
| 内部Wiki | チーム固有の運用手順や設計判断 | Confluence / Notion |

目的に応じて参照すべきドキュメントの種類が異なる。「使い方を知りたい」ならAPIリファレンス、「なぜそう設計されているか」ならコンセプト解説を読む。

### 効率的な読み方の戦略

**1. 目次（Table of Contents）から構造を把握する**

ドキュメントの全体構造を先に理解すれば、必要なセクションに直接アクセスできる。

**2. 検索機能を活用する**

Ctrl+F（ページ内検索）やサイト内検索で、キーワードを使って該当箇所を直接探す。同義語や英語表記で見つからない場合は、キーワードを変えて再検索する。

**3. コード例から逆引きする**

説明文が難しい場合、コード例を先に見て動作を理解し、その後で説明文に戻る。多くの開発者がこの方法で効率的に学んでいる。

**4. バージョンを確認する**

ドキュメントのバージョンが自分の使用しているライブラリのバージョンと一致しているか確認する。バージョン違いのドキュメントを参照すると、存在しないAPIを呼び出したり、非推奨のメソッドを使ったりする。

**5. 変更履歴を確認する**

バージョンアップ時は、ChangelogやMigration Guideを読んで、破壊的変更（Breaking Changes）を把握する。

### ドキュメントが不完全な場合の対処

実際の現場では、ドキュメントが古い・不完全・存在しないケースが少なくない。その場合の対処方法は以下の通りである。

1. **ソースコードを読む**: 最も正確な「ドキュメント」はコードそのものである。型定義やテストコードは特に有用である。
2. **GitのコミットログやPRを確認する**: 変更の経緯や意図が記録されていることがある。
3. **公式のIssueやDiscussionを検索する**: 同じ疑問を持った人がすでに質問している可能性がある。
4. **チームメンバーに聞く**: 上記を試した上で、調べた内容と疑問点を整理して質問する。

## 4) 実務解釈シナリオ

### シナリオ A
- 状況: 外部決済APIを統合する必要がある。公式ドキュメントにAPIリファレンスとチュートリアルがある。
- 行動計画:
  - まずチュートリアル（Getting Started）で全体の流れを把握する。
  - 次にAPIリファレンスで必要なエンドポイントのパラメータとレスポンス形式を確認する。
  - バージョン番号を確認し、自分のSDKバージョンと一致するドキュメントを参照する。
  - 認証方式のセクションを重点的に読む（決済APIでは認証が最も重要）。

### シナリオ B
- 状況: 社内フレームワークのドキュメントが1年以上更新されておらず、記載されているAPIが実際のコードと異なる。
- 対処:
  - ドキュメントの情報を鵜呑みにせず、実際のソースコードの型定義を確認する。
  - 最近のGitコミットログを確認し、APIの変更経緯を把握する。
  - 調査結果を整理し、チームメンバーに確認した上で、ドキュメントの更新を提案する。
  - 自分が正しい情報を確認できたら、ドキュメントを更新する（チームへの貢献になる）。

## 5) よくあるミス

1. ドキュメントを頭から最後まで読もうとする。
目的に合ったセクションだけを読めば十分な場合がほとんどである。

2. バージョンを確認せずにドキュメントを参照する。
存在しないAPIを使おうとしたり、非推奨のパターンで実装してしまう。

3. 公式ドキュメントよりもブログ記事やStack Overflowの回答を優先する。
コミュニティの情報は便利だが、古い情報や不正確な情報が混在している。公式を基本とし、コミュニティは補助として使う。

4. ドキュメントが不完全な時に、推測だけで実装を進める。
ソースコード、コミットログ、Issueなど他の情報源を確認するステップを省略する。

5. 自分が得た知見を記録しない。
同じ調査を将来また行うことになり、チームの知識共有にもつながらない。

## 6) 確認質問

1. 技術ドキュメントの主な種類を3つ以上挙げ、それぞれの目的を説明せよ。
2. ドキュメントのバージョンを確認すべき理由は何か？
3. ドキュメントが古い場合、最も正確な情報源は何か？
4. 公式ドキュメントとブログ記事の使い分けはどうすべきか？
5. ドキュメントで必要な情報を素早く見つけるための戦略を2つ挙げよ。

## 7) 出題抽出メモ

- 事実型候補: ドキュメントの種類と目的、効率的な読み方の戦略
- 判断型候補: 状況に応じた適切なドキュメント種類の選択
- シナリオ型候補: 外部API統合時の読み方、古いドキュメントへの対処
- 誤答誘導ポイント: ブログ記事を公式より優先する、バージョン確認を省略する
