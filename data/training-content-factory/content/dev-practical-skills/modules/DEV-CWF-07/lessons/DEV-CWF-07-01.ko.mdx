## 1) 학습 목표

- 기술 문서의 종류와 각각의 목적을 설명할 수 있다.
- 문서에서 필요한 정보를 빠르게 찾는 전략을 설명할 수 있다.
- 문서가 오래되었거나 불완전할 때 대처 방법을 설명할 수 있다.
- 공식 문서와 커뮤니티 자료의 사용 구분을 판단할 수 있다.

## 2) 업무 맥락

개발자의 업무 시간 중 상당 부분은 코드를 작성하는 것이 아니라 문서를 읽는 데 쓰인다. 새 라이브러리 도입, API 통합, 프레임워크 버전 업그레이드 등 모든 상황에서 문서를 참조해야 한다. 하지만 문서의 양은 방대하고, 전부 처음부터 읽을 시간은 없다. "필요한 정보를 최단 시간에 찾는" 능력은 개발 속도에 직결되는 실무 스킬이다.

## 3) 핵심 설명

### 기술 문서의 종류

| 종류 | 목적 | 예시 |
|------|------|------|
| README | 프로젝트 개요, 셋업 절차 | GitHub 리포지토리의 README.md |
| API 레퍼런스 | 엔드포인트, 파라미터, 응답 스펙 | Swagger / OpenAPI |
| 튜토리얼 | 순서대로 따라하며 배우는 입문 가이드 | Getting Started |
| 가이드(How-to) | 특정 작업의 구현 방법 | 인증 구현 방법 |
| 개념 설명 | 설계 사상이나 구조 설명 | 아키텍처 개요 |
| 변경 이력(Changelog) | 버전별 변경 내용 | CHANGELOG.md |
| 내부 위키 | 팀 고유의 운영 절차나 설계 판단 | Confluence / Notion |

목적에 따라 참조할 문서의 종류가 다르다. "사용법을 알고 싶다"면 API 레퍼런스를, "왜 그렇게 설계되었는가"를 알고 싶다면 개념 설명을 읽는다.

### 효율적인 읽기 전략

**1. 목차(Table of Contents)에서 구조를 파악한다**

문서의 전체 구조를 먼저 이해하면 필요한 섹션에 바로 접근할 수 있다.

**2. 검색 기능을 활용한다**

Ctrl+F(페이지 내 검색)나 사이트 내 검색으로 키워드를 사용해 해당 부분을 직접 찾는다. 동의어나 영어 표기로 검색되지 않으면 키워드를 바꿔서 재검색한다.

**3. 코드 예제에서 역추적한다**

설명이 어려운 경우, 코드 예제를 먼저 보고 동작을 이해한 뒤 설명으로 돌아간다. 많은 개발자가 이 방법으로 효율적으로 학습한다.

**4. 버전을 확인한다**

문서의 버전이 자신이 사용하는 라이브러리 버전과 일치하는지 확인한다. 버전이 다른 문서를 참조하면 존재하지 않는 API를 호출하거나 비권장 메서드를 사용하게 된다.

**5. 변경 이력을 확인한다**

버전 업그레이드 시에는 Changelog나 Migration Guide를 읽어 파괴적 변경(Breaking Changes)을 파악한다.

### 문서가 불완전한 경우의 대처

실제 현장에서는 문서가 오래되었거나, 불완전하거나, 아예 없는 경우가 적지 않다. 그때의 대처 방법은 다음과 같다.

1. **소스 코드를 읽는다**: 가장 정확한 "문서"는 코드 그 자체다. 타입 정의나 테스트 코드가 특히 유용하다.
2. **Git 커밋 로그나 PR을 확인한다**: 변경의 경위나 의도가 기록되어 있을 수 있다.
3. **공식 Issue나 Discussion을 검색한다**: 같은 의문을 가진 사람이 이미 질문했을 가능성이 있다.
4. **팀원에게 물어본다**: 위 방법을 시도한 뒤, 조사한 내용과 의문점을 정리해서 질문한다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 상황: 외부 결제 API를 통합해야 한다. 공식 문서에 API 레퍼런스와 튜토리얼이 있다.
- 행동 계획:
  - 먼저 튜토리얼(Getting Started)로 전체 흐름을 파악한다.
  - 다음으로 API 레퍼런스에서 필요한 엔드포인트의 파라미터와 응답 형식을 확인한다.
  - 버전 번호를 확인하고, 자신의 SDK 버전과 일치하는 문서를 참조한다.
  - 인증 방식 섹션을 중점적으로 읽는다 (결제 API에서 인증이 가장 중요).

### 시나리오 B
- 상황: 사내 프레임워크 문서가 1년 이상 갱신되지 않아, 기재된 API가 실제 코드와 다르다.
- 대처:
  - 문서 정보를 그대로 믿지 말고, 실제 소스 코드의 타입 정의를 확인한다.
  - 최근 Git 커밋 로그를 확인해 API 변경 경위를 파악한다.
  - 조사 결과를 정리하고 팀원에게 확인한 뒤, 문서 업데이트를 제안한다.
  - 자신이 올바른 정보를 확인했으면 문서를 갱신한다 (팀에 대한 기여가 된다).

## 5) 자주 하는 실수

1. 문서를 처음부터 끝까지 읽으려 한다.
목적에 맞는 섹션만 읽으면 충분한 경우가 대부분이다.

2. 버전을 확인하지 않고 문서를 참조한다.
존재하지 않는 API를 사용하려 하거나, 비권장 패턴으로 구현하게 된다.

3. 공식 문서보다 블로그 글이나 Stack Overflow 답변을 우선한다.
커뮤니티 정보는 편리하지만 오래된 정보나 부정확한 정보가 섞여 있다. 공식을 기본으로 하고, 커뮤니티는 보조로 사용한다.

4. 문서가 불완전할 때 추측만으로 구현을 진행한다.
소스 코드, 커밋 로그, Issue 등 다른 정보원을 확인하는 단계를 생략한다.

5. 자신이 얻은 지식을 기록하지 않는다.
같은 조사를 나중에 다시 하게 되고, 팀 지식 공유에도 이어지지 않는다.

## 6) 확인 질문

1. 기술 문서의 주요 종류를 3가지 이상 들고, 각각의 목적을 설명하라.
2. 문서의 버전을 확인해야 하는 이유는 무엇인가?
3. 문서가 오래되었을 때 가장 정확한 정보원은 무엇인가?
4. 공식 문서와 블로그 글의 사용 구분은 어떻게 해야 하는가?
5. 문서에서 필요한 정보를 빠르게 찾기 위한 전략을 2가지 들어라.

## 7) 문항 발췌 메모

- 사실형 후보: 문서의 종류와 목적, 효율적 읽기 전략
- 판단형 후보: 상황에 맞는 적절한 문서 종류 선택
- 시나리오형 후보: 외부 API 통합 시 읽는 방법, 오래된 문서 대처
- 오답 유도 포인트: 블로그 글을 공식보다 우선, 버전 확인 생략
