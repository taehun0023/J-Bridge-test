## 1) 학습 목표

- List, Set, Map의 특성을 비교하고 상황에 맞는 선택 기준을 설명할 수 있다.
- Stream API의 filter, map, collect 파이프라인을 읽고 처리 내용을 추적할 수 있다.
- Stream과 for 루프 중 어느 쪽이 적절한지 판단할 수 있다.
- Stream 사용 시 성능상 주의점을 3가지 이상 설명할 수 있다.

## 2) 업무 맥락

업무 애플리케이션에서는 대량의 데이터를 검색, 변환, 집계하는 처리가 빈번하게 발생한다. 예를 들어 수주 목록에서 특정 조건의 데이터를 추출해 CSV로 변환하여 출력하는 처리다. Java 8 이후의 Stream API를 사용하면 이런 처리를 선언적으로 작성할 수 있다. 하지만 Stream을 오용하면 성능이 저하되거나 가독성이 떨어진다. 실무 코드를 정확히 읽으려면 컬렉션의 특성과 Stream의 동작 원리를 이해하는 것이 필수다.

## 3) 핵심 설명

### 컬렉션 선택 기준

| 컬렉션 | 특성 | 주요 용도 |
|---|---|---|
| `ArrayList` | 순서 있음, 인덱스 접근 O(1) | 목록 표시, 순차 처리 |
| `LinkedList` | 선두/말미 삽입/삭제 O(1) | 큐 구현 |
| `HashSet` | 중복 불가, 순서 없음, 검색 O(1) | 고유성 체크 |
| `TreeSet` | 중복 불가, 정렬 상태 유지 | 범위 검색 |
| `HashMap` | 키→값 매핑, 검색 O(1) | 캐시, 룩업 |
| `TreeMap` | 키 정렬 상태 유지 | 정렬된 매핑 |

선택 기본 원칙: 중복 허용 여부 → List/Set, 순서 필요 여부 → ArrayList/LinkedList 또는 TreeSet/TreeMap, 키로 검색하는지 → Map.

### Stream API 기본 파이프라인

Stream은 **소스 → 중간 연산 → 종단 연산** 3단계로 구성된다.

```java
List<Order> highValueOrders = orders.stream()          // 소스
    .filter(o -> o.getAmount() > 10000)                // 중간 연산: 조건 필터
    .sorted(Comparator.comparing(Order::getCreatedAt)) // 중간 연산: 정렬
    .collect(Collectors.toList());                      // 종단 연산: 리스트로 수집
```

중간 연산은 **지연 평가**된다. 종단 연산이 호출될 때까지 실제 처리는 실행되지 않는다.

### 자주 쓰는 Stream 연산

```java
// map: 요소 변환
List<String> names = users.stream()
    .map(User::getName)
    .collect(Collectors.toList());

// flatMap: 중첩된 컬렉션 평탄화
List<String> allTags = articles.stream()
    .flatMap(a -> a.getTags().stream())
    .distinct()
    .collect(Collectors.toList());

// groupingBy: 그룹화
Map<String, List<Order>> byStatus = orders.stream()
    .collect(Collectors.groupingBy(Order::getStatus));

// reduce: 집계
int totalAmount = orders.stream()
    .mapToInt(Order::getAmount)
    .sum();
```

### 성능 주의점

1. **짧은 리스트(10건 이하)에 Stream을 사용하는 메리트는 적다.** for 루프가 오버헤드가 적다.
2. **parallelStream()은 신중하게 사용한다.** 스레드풀 공유로 인한 예기치 않은 지연이나, 상태를 가진 연산에서의 경합이 발생한다.
3. **Stream은 재사용할 수 없다.** 한 번 종단 연산을 호출하면 같은 Stream 인스턴스를 사용할 수 없다.

## 4) 실무 해석 시나리오

### 시나리오 A
```java
Map<String, Long> categoryCount = products.stream()
    .filter(p -> p.getPrice() > 0)
    .collect(Collectors.groupingBy(
        Product::getCategory,
        Collectors.counting()
    ));
```
- 읽기 포인트:
  - 가격이 0 이하인 무효한 상품을 제외하고 있다.
  - 카테고리별 상품 수를 집계하고 있다.
  - 결과는 `Map<String, Long>`으로 키가 카테고리명, 값이 건수다.

### 시나리오 B
```java
Optional<User> admin = users.stream()
    .filter(u -> "ADMIN".equals(u.getRole()))
    .findFirst();

admin.ifPresentOrElse(
    u -> log.info("Admin found: {}", u.getName()),
    () -> log.warn("No admin user exists")
);
```
- 해석:
  - `findFirst()`는 Stream에서 처음 매칭된 요소를 `Optional`로 반환한다.
  - `ifPresentOrElse`로 존재/부재 양쪽을 처리하고 있다.
  - `"ADMIN".equals(u.getRole())`은 null-safe 비교 패턴이다. `u.getRole().equals("ADMIN")`이면 role이 null일 때 NPE가 발생한다.

## 5) 자주 하는 실수

1. Stream을 변수에 저장해 재사용하려 한다.
Stream은 한 번만 소비할 수 있다. 다시 사용하면 `IllegalStateException`이 발생한다.

2. `collect(Collectors.toList())`의 반환값을 변경 가능하다고 가정한다.
Java 16 이후의 `toList()`는 불변 리스트를 반환한다. 요소 추가가 필요하면 `Collectors.toCollection(ArrayList::new)`를 사용한다.

3. parallelStream()이 항상 빠르다고 생각한다.
작은 데이터셋에서는 스레드 관리 오버헤드가 더 크다.

4. Stream 안에서 외부 변수를 변경한다(부작용).
`forEach` 안에서 외부 리스트에 add하는 것은 스레드 세이프하지 않으며 버그 원인이 된다. `collect`로 결과를 받아야 한다.

5. `Optional.get()`을 검증 없이 호출한다.
값이 존재하지 않을 때 `NoSuchElementException`이 발생한다. `orElse`나 `ifPresent`를 사용해야 한다.
