## 1) 学習目標

- Spring Bootプロジェクトの基本ディレクトリ構造を説明できる。
- 依存性注入（DI）とは何か、なぜ使用するのか説明できる。
- @Component、@Service、@Repository、@Controllerアノテーションの役割を区別できる。
- Bean登録と注入フローをコードで追跡できる。

## 2) 業務コンテキスト

日本のIT現場でSpring Bootは最も広く使用されているバックエンドフレームワークの一つである。新規プロジェクトに投入されると、まずプロジェクトのディレクトリ構造を把握し、どのクラスがどの役割を果たしているかをアノテーションを通じて素早く読む必要がある。依存性注入を理解しなければ、「このオブジェクトがどこで生成されてここに入ってきたのか」を追跡できない。

## 3) 要点解説

Spring Bootプロジェクトは一般的に以下のような構造を持つ。

```
src/main/java/com/example/project/
├── ProjectApplication.java    // エントリーポイント (@SpringBootApplication)
├── controller/                // リクエスト処理層
├── service/                   // ビジネスロジック層
├── repository/                // データアクセス層
├── model/ (またはentity/)     // データモデル
└── config/                    // 設定クラス
src/main/resources/
├── application.yml            // 設定ファイル
└── static/, templates/        // 静的リソース
```

**依存性注入（DI）**はオブジェクトを直接生成せず、フレームワークが必要なオブジェクトを作成して注入する方式である。これによりクラス間の結合度が低くなり、テストが容易になる。

SpringではDIはアノテーションで動作する。
- `@Component`：一般的なSpring管理Beanとして登録する。
- `@Service`：ビジネスロジック層のBean。機能的には@Componentと同じだが、役割を明示する。
- `@Repository`：データアクセス層のBean。データアクセス例外をSpring例外に変換してくれる。
- `@Controller` / `@RestController`：HTTPリクエストを処理する層のBean。

これらのアノテーションが付いたクラスはアプリケーション起動時に自動的にBeanとして登録され、`@Autowired`やコンストラクタ注入を通じて他のBeanに注入される。

**コンストラクタ注入**が現在推奨される方式である。クラスに`final`フィールドとコンストラクタが一つだけあれば、`@Autowired`なしでも自動注入される。

## 4) 実務解釈シナリオ

### シナリオ A
```java
@Service
public class UserService {
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User findById(Long id) {
        return userRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("User not found"));
    }
}
```
- 読み取りポイント：
  - `@Service`でビジネスロジック層であることがわかる。
  - コンストラクタ注入で`UserRepository`を受け取る。Springが自動的に注入する。
  - `findById`はRepositoryに委譲し、見つからなければ例外をスローする。
  - `UserRepository`がどの実装なのかはこのコードだけではわからない — 別途確認が必要である。

### シナリオ B
```java
@RestController
@RequestMapping("/api/users")
public class UserController {
    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<User> getUser(@PathVariable Long id) {
        User user = userService.findById(id);
        return ResponseEntity.ok(user);
    }
}
```
- 解釈：
  - `@RestController`でREST APIエンドポイントを処理する層である。
  - `/api/users/{id}`にGETリクエストが来ると`getUser`メソッドが実行される。
  - Controller → Service → Repositoryの順序で呼び出しが流れる。
  - Controllerはビジネスロジックを直接実装せず、Serviceに委譲する。

## 5) よくあるミス

1. アノテーションなしでクラスを作成し、注入されないと慌てる。
Springが管理するには@Component、@Serviceなどのアノテーションが必ず必要である。

2. フィールド注入（@Autowiredをフィールドに直接使用）を多用する。
フィールド注入はテストしにくく、依存性が隠れてしまう。コンストラクタ注入を使用すべきである。

3. Controllerにビジネスロジックを直接記述する。
Controllerはリクエスト/レスポンス処理のみを担当し、ロジックはServiceに委譲すべきである。

4. パッケージスキャン範囲外にクラスを作成する。
@SpringBootApplicationがあるパッケージとそのサブパッケージのみが自動スキャンされる。

## 6) 確認質問

1. 依存性注入（DI）とは何か、なぜ直接オブジェクトを生成するよりも優れているのか？
2. @Serviceと@Repositoryの違いは何か？
3. コンストラクタ注入がフィールド注入より推奨される理由は何か？
4. @SpringBootApplicationアノテーションの役割は何か？
5. Controllerでビジネスロジックを直接実装するとどのような問題が生じるか？

## 7) 出題抽出メモ

- 事実型候補：Springアノテーション別の役割、DIの定義
- 判断型候補：フィールド注入 vs コンストラクタ注入の適切性
- シナリオ型候補：コードからBean注入フローを追跡、アノテーション欠落時に発生する問題
- 誤答誘導ポイント：@Componentと@Serviceを機能的に完全に異なるものと誤認、パッケージスキャン範囲の無視
