## 1) 학습 목표

- State의 역할과 `useState`의 기본 구문을 설명할 수 있다.
- Props의 역할과 부모-자식 간 데이터 전달 방식을 설명할 수 있다.
- 단방향 데이터 흐름 원칙을 설명할 수 있다.
- State 변경이 컴포넌트 리렌더링을 일으키는 구조를 설명할 수 있다.

## 2) 업무 맥락

React 애플리케이션에서는 사용자 입력이나 API 응답 같은 동적 데이터를 관리해야 한다. State와 Props의 차이를 정확히 이해하지 못하면 데이터 흐름이 복잡해지고, 예상치 못한 UI 동작이나 버그의 원인이 된다. 실무에서는 "어느 컴포넌트가 State를 가져야 하는가"라는 설계 판단이 앱의 유지보수성을 좌우한다.

## 3) 핵심 설명

### State란

State는 컴포넌트가 내부에서 관리하는 변경 가능한 데이터다. `useState` 훅으로 State를 선언한다.

```tsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>카운트: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

**중요한 규칙:**
- State를 직접 변경해서는 안 된다. 반드시 `set 함수`를 사용한다.
- `set 함수`를 호출하면 컴포넌트가 리렌더링된다.
- State 업데이트는 비동기적으로 처리된다(배치 처리).

```tsx
// 잘못된 방법: 직접 변경(UI가 업데이트되지 않음)
count = count + 1;

// 올바른 방법: set 함수 사용
setCount(count + 1);

// 이전 값 기반 업데이트(권장 패턴)
setCount(prev => prev + 1);
```

### Props란

Props는 부모 컴포넌트에서 자식 컴포넌트로 전달되는 데이터다. 자식 측에서는 읽기 전용이며, 변경할 수 없다.

```tsx
// 부모 컴포넌트
function App() {
  const [userName, setUserName] = useState("김철수");
  return <Greeting name={userName} />;
}

// 자식 컴포넌트
function Greeting({ name }: { name: string }) {
  return <h1>안녕하세요, {name}님</h1>;
}
```

### 단방향 데이터 흐름

React의 데이터는 부모에서 자식으로 한 방향으로 흐른다. 자식에서 부모로 데이터를 전달하려면, 콜백 함수를 Props로 넘긴다.

```tsx
function Parent() {
  const [items, setItems] = useState<string[]>([]);

  const handleAdd = (item: string) => {
    setItems(prev => [...prev, item]);
  };

  return (
    <div>
      <ItemInput onAdd={handleAdd} />
      <ItemList items={items} />
    </div>
  );
}

function ItemInput({ onAdd }: { onAdd: (item: string) => void }) {
  const [text, setText] = useState("");

  return (
    <div>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={() => { onAdd(text); setText(""); }}>추가</button>
    </div>
  );
}

function ItemList({ items }: { items: string[] }) {
  return (
    <ul>
      {items.map((item, i) => <li key={i}>{item}</li>)}
    </ul>
  );
}
```

### State 변경과 리렌더링

State가 변경되면 해당 컴포넌트와 모든 자식 컴포넌트가 리렌더링된다.

```
Parent (state 변경) → 리렌더링
  ├── ItemInput → 리렌더링(Props가 바뀌지 않아도)
  └── ItemList  → 리렌더링(Props가 바뀌지 않아도)
```

이것은 성능 문제가 될 수 있지만, 먼저 올바르게 동작하는 코드를 작성하고 문제가 발생한 후 최적화하는 것이 React의 기본 방침이다.

## 4) 실무 해석 시나리오

### 시나리오 A

```tsx
function SearchPage() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState<Item[]>([]);

  const handleSearch = async () => {
    const data = await fetchItems(query);
    setResults(data);
  };

  return (
    <div>
      <SearchBar query={query} onChange={setQuery} onSearch={handleSearch} />
      <ResultList results={results} />
    </div>
  );
}
```

- 읽기 포인트:
  - `query`와 `results` 두 개의 State를 `SearchPage`가 관리하고 있다.
  - `SearchBar`는 Props로 현재 쿼리, 변경 핸들러, 검색 핸들러를 받는다.
  - State "끌어올리기" 패턴: 여러 자식 컴포넌트가 같은 데이터를 공유할 때, 공통 부모에 State를 둔다.

### 시나리오 B

```tsx
function TodoApp() {
  const [todos, setTodos] = useState([
    { id: 1, text: "설계서 작성", done: false },
    { id: 2, text: "코드 리뷰", done: true },
  ]);

  const toggleTodo = (id: number) => {
    setTodos(prev =>
      prev.map(todo =>
        todo.id === id ? { ...todo, done: !todo.done } : todo
      )
    );
  };

  return <TodoList todos={todos} onToggle={toggleTodo} />;
}
```

- 해석:
  - State 업데이트 시 `map`과 스프레드 문법 `{ ...todo, done: !todo.done }`으로 새 배열/객체를 생성하고 있다.
  - 직접 변경(`todo.done = !todo.done`)은 React가 변경을 감지할 수 없으므로 금지다.
  - 불변(immutable) 업데이트 패턴은 React의 기본 원칙이다.

## 5) 자주 하는 실수

1. State를 직접 변경한다(`state.value = newValue`).
React는 참조 변화로 리렌더링을 판단하므로, 직접 변경하면 UI가 업데이트되지 않는다.

2. Props를 State 변수에 매번 복사한다.
`const [localName, setLocalName] = useState(props.name)`은 초기값만 반영된다. Props는 그대로 사용하는 것이 원칙이다.

3. State 업데이트가 비동기라는 것을 잊고 업데이트 직후의 값을 참조한다.
`setCount(count + 1); console.log(count)`의 count는 업데이트 전 값이다.

4. 자식에서 부모에 데이터를 돌려주기 위해 Props를 변경하려 한다.
Props는 읽기 전용이다. 콜백 함수를 사용하여 부모에 데이터를 전달한다.

5. State 배치 위치를 잘못 잡아 불필요한 컴포넌트까지 리렌더링된다.
State는 그것을 필요로 하는 컴포넌트의 가장 가까운 공통 부모에 두어야 한다.
