## 1) 学習目標

- Spring Data JPAのRepository基本パターンを読んで理解できる。
- @Transactionalの動作原理と伝播（Propagation）ルールを説明できる。
- N+1問題の発生原因と解決方法を説明できる。
- 遅延ロード（Lazy Loading）と即時ロード（Eager Loading）の違いと注意点を説明できる。

## 2) 業務コンテキスト

日本のIT現場のSpring Bootプロジェクトでは、データベースアクセスにJPAを使用するケースが非常に多い。しかし、JPAは便利な反面、N+1問題や遅延ロード例外など、理解不足から発生するパフォーマンス問題やランタイムエラーが頻発する。既存コードのレビューや障害調査の際に、これらの問題を見抜く力が求められる。

## 3) 要点解説

**Spring Data JPA Repositoryの基本パターン：**

```java
// Entity定義
@Entity
@Table(name = "employees")
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String department;

    @OneToMany(mappedBy = "employee", fetch = FetchType.LAZY)
    private List<Task> tasks;
}

// Repository定義 — インターフェースのみでCRUDが使える
public interface EmployeeRepository extends JpaRepository<Employee, Long> {

    // メソッド名からクエリ自動生成
    List<Employee> findByDepartment(String department);

    // カスタムクエリ
    @Query("SELECT e FROM Employee e WHERE e.name LIKE %:keyword%")
    List<Employee> searchByName(@Param("keyword") String keyword);
}
```

Spring Data JPAは`JpaRepository`を継承するだけで`save`、`findById`、`findAll`、`delete`などの基本操作が使える。メソッド名の命名規則に従うとSQLを書かずにクエリが自動生成される。

**@Transactionalの動作：**

```java
@Service
public class TransferService {
    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId)
            .orElseThrow(() -> new AccountNotFoundException(fromId));
        Account to = accountRepository.findById(toId)
            .orElseThrow(() -> new AccountNotFoundException(toId));

        from.withdraw(amount);   // 残高不足なら例外
        to.deposit(amount);

        accountRepository.save(from);
        accountRepository.save(to);
        // メソッド正常終了 → 自動COMMIT
        // RuntimeException発生 → 自動ROLLBACK
    }
}
```

`@Transactional`を付けると、メソッド開始時にトランザクションが開始され、正常終了でCOMMIT、RuntimeException発生でROLLBACKされる。チェック例外（Exception）はデフォルトではROLLBACKされない点に注意が必要である。

**伝播（Propagation）の主要パターン：**
- `REQUIRED`（デフォルト）：既存トランザクションがあれば参加、なければ新規作成。
- `REQUIRES_NEW`：常に新しいトランザクションを作成。既存トランザクションは一時停止される。
- `MANDATORY`：既存トランザクションが必須。なければ例外をスローする。

**N+1問題：**

```java
// N+1が発生するコード
List<Employee> employees = employeeRepository.findAll(); // 1回のクエリ
for (Employee emp : employees) {
    System.out.println(emp.getTasks().size()); // 従業員ごとに1回ずつクエリ発行
}
// 従業員が100人なら、合計101回のクエリが発行される
```

`@OneToMany(fetch = FetchType.LAZY)`の場合、関連エンティティはアクセス時に初めてDBに問い合わせる。ループ内でアクセスすると、N件の親エンティティに対してN回の追加クエリが発行される。

**N+1の解決策：**

```java
// 解決策1: Fetch Join
@Query("SELECT e FROM Employee e JOIN FETCH e.tasks")
List<Employee> findAllWithTasks();

// 解決策2: @EntityGraph
@EntityGraph(attributePaths = {"tasks"})
List<Employee> findAll();
```

Fetch Joinまたは`@EntityGraph`を使用すると、1回のクエリで関連エンティティも一緒に取得できる。

**遅延ロード例外（LazyInitializationException）：**

トランザクション外で遅延ロードされたコレクションにアクセスすると`LazyInitializationException`が発生する。ServiceメソッドにTransactionalを付けるか、必要なデータをトランザクション内でDTOに変換して返す。

## 4) 実務解釈シナリオ

### シナリオ A
```java
@Service
public class ReportService {
    @Transactional(readOnly = true)
    public List<EmployeeDto> getEmployeeReport() {
        List<Employee> employees = employeeRepository.findAll();
        return employees.stream()
            .map(e -> new EmployeeDto(e.getName(), e.getTasks().size()))
            .collect(Collectors.toList());
    }
}
```
- 解釈：`readOnly = true`は読み取り専用トランザクションを示し、JPAのダーティチェックが無効化されてパフォーマンスが向上する。しかし、`findAll()`で全従業員を取得した後、`e.getTasks().size()`でN+1問題が発生する。Fetch Joinを使って1クエリで取得すべきである。`@Transactional`があるため`LazyInitializationException`は発生しないが、パフォーマンス問題が残る。

### シナリオ B
```java
@Service
public class OrderService {
    @Transactional
    public void processOrder(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.setStatus(OrderStatus.PROCESSING);
        // save()を呼んでいないが、トランザクション終了時に自動的にUPDATEされる
    }
}
```
- 解釈：JPAのダーティチェック機能により、トランザクション内でEntityのフィールドを変更すると、トランザクションCOMMIT時に自動的にUPDATEクエリが発行される。明示的に`save()`を呼ばなくても変更は反映される。これはJPA初心者が見落としやすいポイントである。

## 5) よくあるミス

1. N+1問題に気づかずにループ内で遅延ロードを実行する。
本番環境でデータ量が増えると急激にパフォーマンスが悪化する。SQLログ（`spring.jpa.show-sql=true`）で発行クエリ数を確認する習慣をつける。

2. チェック例外でROLLBACKされると思い込む。
`@Transactional`はデフォルトでRuntimeExceptionのみROLLBACKする。チェック例外でもROLLBACKしたい場合は`@Transactional(rollbackFor = Exception.class)`を指定する。

3. トランザクション外で遅延ロードコレクションにアクセスする。
Controllerで直接Entityを返すと、JSON変換時にLazyInitializationExceptionが発生する。Service層でDTOに変換して返す。

4. @Transactionalをprivateメソッドに付ける。
Springのプロキシ方式では、privateメソッドの@Transactionalは無視される。publicメソッドに付ける必要がある。

5. 同一クラス内のメソッド呼び出しでトランザクション伝播が効かないことに気づかない。
自己呼び出し（`this.method()`）ではプロキシを経由しないため、@Transactionalが適用されない。別のBeanに分離する必要がある。

## 7) 出題抽出メモ

- 事実型候補：@TransactionalのデフォルトROLLBACK対象、FetchType.LAZYの挙動
- 判断型候補：N+1問題の検出とFetch Join適用判断、readOnlyトランザクションの適用場面
- シナリオ型候補：ループ内で遅延ロードが実行されるコードの問題指摘、save()なしで更新が反映される理由の説明
- 誤答誘導ポイント：チェック例外でもデフォルトROLLBACKされると誤認、privateメソッドの@Transactionalが有効と誤認
