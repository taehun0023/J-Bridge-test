## 1) 학습 목표

- 서버 컴포넌트에서의 데이터 페칭 패턴과 주의사항을 설명할 수 있다.
- Next.js의 캐싱 계층(Request Memoization, Data Cache, Full Route Cache)을 설명할 수 있다.
- 정적 렌더링과 동적 렌더링의 차이와 전환 조건을 설명할 수 있다.
- 대규모 프로젝트에서의 폴더 구성 패턴을 설명할 수 있다.

## 2) 업무 맥락

Next.js 프로젝트에서 데이터를 가져오는 방식은 성능과 사용자 경험에 직접적인 영향을 준다. 서버 컴포넌트에서 데이터를 페칭할 때 캐싱이 어떻게 동작하는지, 언제 정적/동적 렌더링이 선택되는지를 이해하지 못하면 "데이터가 갱신되지 않는다"거나 "빌드 시간이 지나치게 길다"는 문제에 직면한다. 또한 프로젝트가 커지면 폴더 구성 전략이 유지보수성을 결정한다.

## 3) 핵심 설명

### 서버 컴포넌트에서의 데이터 페칭

서버 컴포넌트는 `async/await`로 직접 데이터를 조회할 수 있다. API 라우트를 별도로 만들 필요가 없다.

```tsx
// app/users/page.tsx (서버 컴포넌트)
export default async function UsersPage() {
  const res = await fetch('https://api.example.com/users');
  const users = await res.json();

  return (
    <ul>
      {users.map((user: { id: string; name: string }) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

데이터베이스를 직접 조회하는 것도 가능하다:

```tsx
import { createClient } from '@/lib/supabase/server';

export default async function UsersPage() {
  const supabase = await createClient();
  const { data: users } = await supabase.from('profiles').select('*');
  return <UserList users={users ?? []} />;
}
```

### 병렬 데이터 페칭

여러 데이터를 동시에 가져올 때는 `Promise.all`을 사용하여 병렬로 실행한다. 순차 실행보다 총 대기 시간이 줄어든다.

```tsx
export default async function DashboardPage() {
  const [users, stats, notifications] = await Promise.all([
    fetchUsers(),
    fetchStats(),
    fetchNotifications(),
  ]);

  return (
    <div>
      <UserSection users={users} />
      <StatsSection stats={stats} />
      <NotificationSection notifications={notifications} />
    </div>
  );
}
```

### Next.js 캐싱 계층

Next.js는 여러 단계의 캐싱을 제공한다:

**1. Request Memoization**: 같은 렌더링 과정에서 동일한 `fetch` 요청이 여러 번 호출되면, 실제 요청은 한 번만 실행되고 결과를 재사용한다. 같은 페이지 내 여러 컴포넌트가 같은 데이터를 필요로 할 때 유용하다.

**2. Data Cache**: `fetch` 요청의 결과를 서버에 지속적으로 캐시한다. 재검증(revalidation) 전략으로 갱신 주기를 제어한다.

**3. Full Route Cache**: 빌드 시 정적으로 렌더링된 페이지의 HTML과 RSC Payload를 캐시한다.

### 재검증 전략

```tsx
// 시간 기반 재검증: 60초마다 캐시 갱신
const res = await fetch('https://api.example.com/data', {
  next: { revalidate: 60 }
});

// 캐시 비활성화: 매 요청마다 새로 페칭
const res = await fetch('https://api.example.com/data', {
  cache: 'no-store'
});
```

페이지 단위로 재검증 주기를 설정할 수도 있다:

```tsx
// app/blog/page.tsx
export const revalidate = 3600; // 1시간마다 재검증
```

### 정적 렌더링 vs 동적 렌더링

**정적 렌더링** (기본값): 빌드 시 HTML을 생성한다. 모든 사용자에게 같은 내용을 보여주는 페이지에 적합하다.

**동적 렌더링**: 요청 시마다 HTML을 생성한다. 다음 조건에서 자동으로 동적 렌더링으로 전환된다:
- `cookies()`, `headers()`, `searchParams` 사용
- `cache: 'no-store'`로 fetch 호출
- 동적 라우트에서 `generateStaticParams`가 없는 경우

```tsx
import { cookies } from 'next/headers';

// cookies()를 사용하면 자동으로 동적 렌더링
export default async function ProfilePage() {
  const cookieStore = await cookies();
  const token = cookieStore.get('session');
  // ...
}
```

### 대규모 프로젝트 폴더 구성 패턴

프로젝트가 커지면 코드를 체계적으로 구성하는 것이 중요하다. 실무에서 자주 사용하는 패턴:

**패턴 1: 기능별 그룹화 (라우트 그룹 활용)**
```
app/
├── (admin)/         # 관리자 기능
│   ├── layout.tsx
│   ├── users/
│   └── settings/
├── (main)/          # 일반 사용자 기능
│   ├── layout.tsx
│   ├── dashboard/
│   └── profile/
```

**패턴 2: 컴포넌트 코로케이션 (관련 파일을 함께 배치)**
```
app/dashboard/
├── page.tsx
├── DashboardClient.tsx    # 이 페이지 전용 클라이언트 컴포넌트
├── StatsChart.tsx         # 이 페이지 전용 차트 컴포넌트
└── loading.tsx
```

**패턴 3: 공유 코드 분리**
```
src/
├── app/              # 라우팅 (페이지, 레이아웃)
├── components/       # 공유 UI 컴포넌트
├── lib/              # 유틸리티, 설정
├── modules/          # 도메인 로직 (비즈니스 규칙)
└── app/actions/      # Server Actions
```

## 4) 실무 해석 시나리오

### 시나리오 A
```tsx
// app/products/page.tsx
export const revalidate = 300; // 5분

export default async function ProductsPage() {
  const res = await fetch('https://api.example.com/products');
  const products = await res.json();

  return <ProductList products={products} />;
}
```
```tsx
// app/products/[id]/page.tsx
export default async function ProductDetail({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const res = await fetch(`https://api.example.com/products/${id}`, {
    cache: 'no-store'
  });
  const product = await res.json();

  return <ProductView product={product} />;
}
```
- 읽기 포인트:
  - 상품 목록(`/products`)은 5분마다 재검증되는 정적 페이지다. 자주 변경되지 않는 목록에 적합하다.
  - 상품 상세(`/products/[id]`)는 `cache: 'no-store'`로 매 요청마다 최신 데이터를 가져온다. 재고 등 실시간 정보가 중요한 경우에 적합하다.
  - 같은 도메인(products)이지만 페이지마다 캐싱 전략이 다를 수 있다.

### 시나리오 B
```tsx
// lib/queries.ts
export async function fetchUserProfile(userId: string) {
  const supabase = await createClient();
  const { data } = await supabase
    .from('profiles')
    .select('*, japanese_skills(*), coding_skills(*)')
    .eq('id', userId)
    .single();
  return data;
}

// app/dashboard/page.tsx
import { fetchUserProfile } from '@/lib/queries';
import { requireAuth } from '@/lib/auth-helpers';

export default async function DashboardPage() {
  const user = await requireAuth();
  const profile = await fetchUserProfile(user.id);

  return <DashboardClient profile={profile} />;
}
```
- 해석:
  - 데이터 조회 로직을 `lib/queries.ts`에 분리하여 재사용성을 높인 패턴이다.
  - `requireAuth()`로 인증을 확인하고, 인증된 사용자의 프로필을 조회한다.
  - `cookies()`를 내부적으로 사용하는 `requireAuth` 때문에 이 페이지는 자동으로 동적 렌더링된다.
  - 서버에서 조회한 데이터를 클라이언트 컴포넌트에 props로 전달하는 표준 패턴이다.

## 5) 자주 하는 실수

1. 모든 페이지에서 캐시를 비활성화(`cache: 'no-store'`)한다.
캐시를 전부 끄면 성능 이점을 잃는다. 실시간성이 필요한 데이터만 선별적으로 비활성화해야 한다.

2. 순차적으로 데이터를 페칭하여 워터폴(waterfall)을 만든다.
독립적인 데이터 요청은 `Promise.all`로 병렬 실행해야 한다. 순차 실행은 총 대기 시간을 불필요하게 늘린다.

3. 동적 함수(`cookies()`, `headers()`)를 사용하면서 정적 렌더링을 기대한다.
동적 함수를 사용하면 자동으로 동적 렌더링으로 전환된다. 의도적인 것인지 확인해야 한다.

4. 클라이언트 컴포넌트에서 직접 데이터베이스를 조회하려 한다.
데이터 페칭은 서버 컴포넌트나 Server Action에서 수행하고, 결과만 클라이언트에 전달해야 한다.

5. `revalidate` 값을 설정하지 않고 데이터가 갱신되지 않는다고 혼란스러워한다.
기본적으로 `fetch`는 결과를 캐시한다. 데이터 갱신이 필요하면 `revalidate` 시간을 명시하거나 `cache: 'no-store'`를 사용해야 한다.
