## 1) 학습 목표

- `useEffect`의 실행 타이밍과 의존성 배열의 관계를 설명할 수 있다.
- 의존성 배열이 빈 배열 `[]`, 지정 있음 `[dep]`, 생략의 3가지 패턴 차이를 설명할 수 있다.
- 클린업 함수의 목적과 실행 타이밍을 설명할 수 있다.
- `useEffect` 내에서 비동기 처리를 다루는 패턴을 설명할 수 있다.

## 2) 업무 맥락

프론트엔드 개발에서는 컴포넌트 마운트 시 API 호출, 특정 값 변경 시 데이터 재조회, 언마운트 시 리스너 해제 등 사이드 이펙트 관리가 필요하다. `useEffect`의 의존성 배열을 올바르게 설정하지 않으면 무한 루프, 오래된 데이터 표시, 메모리 누수 같은 문제가 발생한다.

## 3) 핵심 설명

### useEffect 기본

`useEffect`는 렌더링 후 사이드 이펙트를 실행하는 훅이다.

```tsx
import { useState, useEffect } from "react";

function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    // 사이드 이펙트: API에서 데이터 가져오기
    fetchUser(userId).then(data => setUser(data));
  }, [userId]); // userId가 바뀔 때만 실행

  if (!user) return <p>불러오는 중...</p>;
  return <p>{user.name}</p>;
}
```

### 의존성 배열 3가지 패턴

```tsx
// 패턴 1: 의존성 배열 있음 → 지정한 값이 바뀔 때 실행
useEffect(() => {
  console.log("userId가 바뀌었다:", userId);
}, [userId]);

// 패턴 2: 빈 배열 → 마운트 시 1회만 실행
useEffect(() => {
  console.log("컴포넌트가 마운트됨");
}, []);

// 패턴 3: 의존성 배열 없음 → 매 렌더링 후 실행(보통 비권장)
useEffect(() => {
  console.log("매번 실행됨");
});
```

**의존성 배열 판단 기준:** Effect 내에서 참조하는 외부 값(state, props, 함수 등)은 모두 의존성 배열에 포함해야 한다. ESLint의 `react-hooks/exhaustive-deps` 규칙이 이를 감지한다.

### 클린업 함수

`useEffect`에서 return하는 함수가 클린업 함수다. 다음 Effect 실행 전과 언마운트 시에 호출된다.

```tsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(prev => prev + 1);
    }, 1000);

    // 클린업: 언마운트 시 인터벌 해제
    return () => clearInterval(id);
  }, []); // 마운트 시 1회 설정

  return <p>{seconds}초</p>;
}
```

클린업을 빠뜨리면 언마운트 후에도 인터벌이나 이벤트 리스너가 계속 동작하여 메모리 누수나 에러의 원인이 된다.

```tsx
function WindowSize() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", handleResize);

    return () => window.removeEventListener("resize", handleResize);
  }, []);

  return <p>너비: {width}px</p>;
}
```

### 비동기 처리 패턴

`useEffect`의 콜백 자체를 `async`로 만들 수는 없다. 내부에서 비동기 함수를 정의하여 호출한다.

```tsx
useEffect(() => {
  // NG: useEffect(() => async () => { ... })
  // OK: 내부에서 async 함수 정의
  const fetchData = async () => {
    try {
      const response = await fetch(`/api/users/${userId}`);
      const data = await response.json();
      setUser(data);
    } catch (error) {
      setError("가져오기에 실패했습니다");
    }
  };

  fetchData();
}, [userId]);
```

### 경쟁 상태(Race Condition) 대처

의존 값이 짧은 시간에 연속으로 바뀌면, 오래된 요청의 결과가 새 요청의 결과를 덮어쓸 수 있다.

```tsx
useEffect(() => {
  let cancelled = false;

  const fetchData = async () => {
    const data = await fetchUser(userId);
    if (!cancelled) {
      setUser(data);  // 취소되지 않았을 때만 업데이트
    }
  };

  fetchData();
  return () => { cancelled = true; };  // 다음 Effect 실행 시 취소
}, [userId]);
```

## 4) 실무 해석 시나리오

### 시나리오 A

```tsx
function NotificationBell() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const ws = new WebSocket("wss://api.example.com/notifications");
    ws.onmessage = () => setCount(prev => prev + 1);
    return () => ws.close();
  }, []);

  return <span>알림 {count}</span>;
}
```

- 읽기 포인트:
  - 마운트 시 WebSocket 연결을 수립하고, 메시지 수신마다 카운트를 증가시킨다.
  - 빈 의존성 배열 `[]`로 연결은 1회만 이루어진다.
  - 클린업에서 `ws.close()`를 호출하여 언마운트 시 연결을 확실히 끊는다.

### 시나리오 B

```tsx
function SearchResults({ query }: { query: string }) {
  const [results, setResults] = useState<Item[]>([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!query) {
      setResults([]);
      return;
    }

    let cancelled = false;
    setLoading(true);

    searchItems(query).then(data => {
      if (!cancelled) {
        setResults(data);
        setLoading(false);
      }
    });

    return () => { cancelled = true; };
  }, [query]);

  if (loading) return <p>검색 중...</p>;
  return <ResultList items={results} />;
}
```

- 해석:
  - `query`가 바뀔 때마다 검색이 실행된다.
  - `cancelled` 플래그로 오래된 요청의 결과를 버리고 경쟁 상태를 방지하고 있다.
  - `query`가 비어있으면 조기 리턴으로 불필요한 API 호출을 피한다.

## 5) 자주 하는 실수

1. 의존성 배열에 Effect 내에서 사용하는 값을 넣지 않는다.
오래된 값(stale closure)이 참조되어 의도하지 않은 동작이 된다. ESLint 규칙을 따라야 한다.

2. 의존성 배열을 생략하여 매 렌더링마다 실행된다.
API 호출이 매 렌더링에서 발생하여 무한 루프가 될 수 있다.

3. 클린업 함수를 작성하지 않아 메모리 누수가 생긴다.
타이머, 이벤트 리스너, WebSocket 연결은 반드시 클린업이 필요하다.

4. `useEffect`의 콜백을 직접 `async`로 만든다.
`useEffect(() => async () => { ... })`는 Promise를 반환하여 클린업이 정상 동작하지 않는다.

5. 경쟁 상태를 고려하지 않고 비동기 데이터를 가져온다.
의존 값의 빠른 변경으로 오래된 결과가 새 결과를 덮어쓰는 버그가 발생한다.

## 7) 문항 발췌 메모

- 사실형 후보: 의존성 배열 3가지 패턴과 실행 타이밍, 클린업 함수의 호출 타이밍

- 오답 유도 포인트: useEffect 콜백을 async로 만들 수 있다고 착각, 빈 배열은 매번 실행된다고 착각
