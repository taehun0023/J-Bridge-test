## 1) 学習目標

- 開発・ステージング・本番環境の違いと分離する理由を説明できる。
- 環境変数と設定ファイルの役割を区別できる。
- 設定関連の障害について原因を推論できる。
- `.env`ファイルの基本的な構造と注意点を説明できる。

## 2) 業務コンテキスト

ソフトウェア開発では、コードは一つでも動作する環境は複数存在する。開発中のローカル環境、テスト用のステージング環境、実際のユーザーが利用する本番環境である。環境ごとにデータベース接続先やAPIキー、ログレベルなどが異なるため、設定を正しく管理し読み取る能力は、コードを書く能力と同等に重要である。設定ミスによる障害は現場で頻繁に発生し、原因特定に時間がかかることが多い。

## 3) 要点解説

### 環境分離の理由

環境を分離する最大の理由は「本番データとサービスを守ること」である。

| 環境 | 目的 | データ | アクセス |
|------|------|--------|----------|
| 開発（Development） | 機能実装・デバッグ | テストデータ | 開発者のみ |
| ステージング（Staging） | 本番リリース前の検証 | 本番に近いデータ | チーム内部 |
| 本番（Production） | 実ユーザーへのサービス提供 | 実データ | 全ユーザー |

開発環境で本番データベースに接続してしまうと、テスト中に実データを破壊するリスクがある。逆に、本番環境でデバッグ用の設定が残っていると、パフォーマンス低下や情報漏洩の原因になる。

### 設定ファイルの種類

環境ごとの設定を管理する方法は主に以下の3つである。

**1. 環境変数（Environment Variables）**

```bash
DATABASE_URL=postgresql://localhost:5432/myapp_dev
API_KEY=dev-key-12345
LOG_LEVEL=debug
```

環境変数はOSレベルで設定され、アプリケーションが起動時に読み込む。秘密情報（APIキー、DB接続文字列）は環境変数で管理するのが一般的である。

**2. `.env`ファイル**

```
# .env.development
DATABASE_URL=postgresql://localhost:5432/myapp_dev
NEXT_PUBLIC_API_URL=http://localhost:3000/api

# .env.production
DATABASE_URL=postgresql://prod-server:5432/myapp_prod
NEXT_PUBLIC_API_URL=https://api.example.com
```

`.env`ファイルは環境変数をファイルとして管理する仕組みである。通常、`.env`ファイルはGitにコミットしない（`.gitignore`に追加する）。

**3. 設定ファイル（JSON / YAML）**

```json
{
  "development": {
    "logLevel": "debug",
    "featureFlags": { "newUI": true }
  },
  "production": {
    "logLevel": "error",
    "featureFlags": { "newUI": false }
  }
}
```

機能フラグやログレベルなど、秘密でない設定は設定ファイルで管理することが多い。

### 設定の優先順位

多くのフレームワークでは、設定の読み込みに優先順位がある。一般的には以下の順序で後のものが前のものを上書きする。

1. デフォルト設定（コード内のハードコード）
2. 設定ファイル（`config.json`など）
3. `.env`ファイル
4. OS環境変数
5. コマンドライン引数

この優先順位を理解していないと、「設定ファイルを変更したのに反映されない」という問題に悩まされることがある。

## 4) 実務解釈シナリオ

### シナリオ A
- 状況: ローカル環境では正常に動作するAPIが、ステージング環境にデプロイすると500エラーを返す。
- ログ: `Error: Missing environment variable: STRIPE_SECRET_KEY`
- 解釈:
  - ローカルの`.env`ファイルにはAPIキーが設定されていたが、ステージング環境の環境変数に設定されていない。
  - `.env`ファイルはGitにコミットされないため、デプロイ先で別途設定が必要である。
  - 対応: ステージング環境のCI/CDまたはホスティングサービスの環境変数設定を確認する。

### シナリオ B
- 状況: 本番環境でユーザーの個人情報がログに出力されていることが判明した。
- 原因調査: `LOG_LEVEL=debug`が本番環境に設定されていた。
- 解釈:
  - デバッグレベルのログはリクエストボディなど詳細情報を出力するため、本番では`error`または`warn`に設定すべきである。
  - 環境ごとの設定レビューが行われていなかった可能性がある。
  - 対応: 即座にログレベルを変更し、出力済みのログの取り扱いをセキュリティチームに相談する。

## 5) よくあるミス

1. `.env`ファイルをGitリポジトリにコミットする。
秘密情報が公開リポジトリに流出し、セキュリティインシデントになる。

2. ローカルの`.env`を本番用の値に書き換えて開発する。
本番データベースに対してテストデータを投入してしまうリスクがある。

3. 環境変数の設定漏れをデプロイ後に気づく。
起動時にエラーが出ない場合、実行時に初めて発覚し障害につながる。

4. 設定の優先順位を理解せず、変更が反映されない原因を探し続ける。
OS環境変数が`.env`を上書きしていることに気づかないケースが多い。

5. 全環境で同じ設定値を使い回す。
本番と開発でログレベルやエラー詳細表示が同一になり、セキュリティリスクが生まれる。

## 6) 確認質問

1. 環境を分離する最大の理由は何か？
2. 秘密情報をコード内にハードコードしてはいけない理由は何か？
3. `.env`ファイルを`.gitignore`に追加すべき理由は何か？
4. ステージング環境にデプロイ後に環境変数関連のエラーが出た場合、最初に確認すべきことは何か？
5. `LOG_LEVEL=debug`が本番環境に設定されていた場合のリスクは何か？

## 7) 出題抽出メモ

- 事実型候補: 3つの環境の目的と違い、設定の優先順位
- 判断型候補: 環境変数エラー時の原因推論
- シナリオ型候補: デプロイ後の設定漏れエラー、本番環境のログレベル設定ミス
- 誤答誘導ポイント: `.env`と環境変数の優先順位の混同、秘密情報の管理場所の誤解
