## 1) 학습 목표

- 개발, 스테이징, 운영 환경의 차이와 분리하는 이유를 설명할 수 있다.
- 환경 변수와 설정 파일의 역할을 구분할 수 있다.
- 설정 관련 장애의 원인을 추론할 수 있다.
- `.env` 파일의 기본 구조와 주의점을 설명할 수 있다.

## 2) 업무 맥락

소프트웨어 개발에서 코드는 하나지만 동작하는 환경은 여러 개 존재한다. 개발 중인 로컬 환경, 테스트용 스테이징 환경, 실제 사용자가 이용하는 운영 환경이다. 환경마다 데이터베이스 접속 정보나 API 키, 로그 레벨 등이 다르기 때문에 설정을 올바르게 관리하고 읽는 능력은 코드 작성 능력만큼 중요하다. 설정 실수로 인한 장애는 현장에서 빈번하게 발생하며, 원인 파악에 시간이 많이 걸리는 경우가 많다.

## 3) 핵심 설명

### 환경 분리의 이유

환경을 분리하는 가장 큰 이유는 "운영 데이터와 서비스를 보호하는 것"이다.

| 환경 | 목적 | 데이터 | 접근 |
|------|------|--------|------|
| 개발(Development) | 기능 구현·디버깅 | 테스트 데이터 | 개발자만 |
| 스테이징(Staging) | 운영 릴리스 전 검증 | 운영과 유사한 데이터 | 팀 내부 |
| 운영(Production) | 실 사용자 서비스 제공 | 실 데이터 | 전체 사용자 |

개발 환경에서 운영 데이터베이스에 접속하면 테스트 도중 실 데이터를 파괴할 위험이 있다. 반대로, 운영 환경에 디버그 설정이 남아 있으면 성능 저하나 정보 유출 원인이 된다.

### 설정 파일의 종류

환경별 설정을 관리하는 방법은 크게 세 가지다.

**1. 환경 변수(Environment Variables)**

```bash
DATABASE_URL=postgresql://localhost:5432/myapp_dev
API_KEY=dev-key-12345
LOG_LEVEL=debug
```

환경 변수는 OS 수준에서 설정되며, 애플리케이션이 시작할 때 읽어들인다. 비밀 정보(API 키, DB 접속 문자열)는 환경 변수로 관리하는 것이 일반적이다.

**2. `.env` 파일**

```
# .env.development
DATABASE_URL=postgresql://localhost:5432/myapp_dev
NEXT_PUBLIC_API_URL=http://localhost:3000/api

# .env.production
DATABASE_URL=postgresql://prod-server:5432/myapp_prod
NEXT_PUBLIC_API_URL=https://api.example.com
```

`.env` 파일은 환경 변수를 파일로 관리하는 방식이다. 보통 `.env` 파일은 Git에 커밋하지 않는다(`.gitignore`에 추가).

**3. 설정 파일(JSON / YAML)**

```json
{
  "development": {
    "logLevel": "debug",
    "featureFlags": { "newUI": true }
  },
  "production": {
    "logLevel": "error",
    "featureFlags": { "newUI": false }
  }
}
```

기능 플래그나 로그 레벨 등 비밀이 아닌 설정은 설정 파일로 관리하는 경우가 많다.

### 설정의 우선순위

대부분의 프레임워크에서 설정 읽기에는 우선순위가 있다. 일반적으로 뒤의 것이 앞의 것을 덮어쓴다.

1. 기본 설정 (코드 내 하드코딩)
2. 설정 파일 (`config.json` 등)
3. `.env` 파일
4. OS 환경 변수
5. 커맨드라인 인수

이 우선순위를 이해하지 못하면 "설정 파일을 바꿨는데 반영이 안 된다"는 문제로 고생하게 된다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 상황: 로컬 환경에서는 정상 동작하는 API가 스테이징 환경에 배포하면 500 에러를 반환한다.
- 로그: `Error: Missing environment variable: STRIPE_SECRET_KEY`
- 해석:
  - 로컬의 `.env` 파일에는 API 키가 설정되어 있었지만, 스테이징 환경의 환경 변수에는 설정되지 않았다.
  - `.env` 파일은 Git에 커밋되지 않으므로 배포 대상에서 별도 설정이 필요하다.
  - 대응: 스테이징 환경의 CI/CD 또는 호스팅 서비스의 환경 변수 설정을 확인한다.

### 시나리오 B
- 상황: 운영 환경에서 사용자의 개인 정보가 로그에 출력되고 있음이 발견되었다.
- 원인 조사: `LOG_LEVEL=debug`가 운영 환경에 설정되어 있었다.
- 해석:
  - 디버그 수준 로그는 요청 본문 등 상세 정보를 출력하므로, 운영에서는 `error` 또는 `warn`으로 설정해야 한다.
  - 환경별 설정 리뷰가 이루어지지 않았을 가능성이 있다.
  - 대응: 즉시 로그 레벨을 변경하고, 이미 출력된 로그 처리를 보안 팀과 상의한다.

## 5) 자주 하는 실수

1. `.env` 파일을 Git 리포지토리에 커밋한다.
비밀 정보가 공개 리포지토리에 유출되어 보안 사고가 된다.

2. 로컬의 `.env`를 운영용 값으로 바꾸어 개발한다.
운영 데이터베이스에 테스트 데이터를 넣어버릴 위험이 있다.

3. 환경 변수 설정 누락을 배포 후에야 깨닫는다.
시작 시 에러가 나지 않으면 실행 중에야 비로소 발견되어 장애로 이어진다.

4. 설정의 우선순위를 이해하지 못해 변경이 반영되지 않는 원인을 계속 찾는다.
OS 환경 변수가 `.env`를 덮어쓰고 있음을 모르는 경우가 많다.

5. 모든 환경에서 같은 설정값을 사용한다.
운영과 개발에서 로그 레벨이나 에러 상세 표시가 동일해져 보안 위험이 생긴다.

4. 스테이징 환경에 배포 후 환경 변수 관련 에러가 발생했을 때 가장 먼저 확인할 것은?
5. `LOG_LEVEL=debug`가 운영 환경에 설정되어 있을 때의 위험은 무엇인가?
