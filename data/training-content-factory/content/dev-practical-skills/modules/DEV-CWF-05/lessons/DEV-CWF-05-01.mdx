## 1) 学習目標

- HTTPリクエストの構成要素（メソッド、ヘッダー、ボディ）を説明できる。
- ステータスコード（2xx / 4xx / 5xx）の意味を区分できる。
- APIレスポンスからエラーメッセージを読み取り、原因を推論できる。
- よく使われるHTTPメソッド（GET / POST / PUT / DELETE）の違いを説明できる。

## 2) 業務コンテキスト

現代のWebアプリケーションはほぼすべてAPIを通じてデータをやり取りする。フロントエンドとバックエンドの間、あるいはサービス間の通信はHTTPプロトコルに基づいている。開発中に「APIが動かない」という状況に遭遇した時、リクエストとレスポンスの構造を正しく読めなければ、原因の特定に無駄な時間を費やすことになる。ステータスコードの意味を知っているだけで、問題の所在（クライアント側かサーバー側か）を即座に判断できる。

## 3) 要点解説

### HTTPリクエストの構造

HTTPリクエストは以下の3つの主要部分で構成される。

**1. リクエストライン**
```
GET /api/users/123 HTTP/1.1
```
メソッド（GET）、パス（/api/users/123）、HTTPバージョンが含まれる。

**2. ヘッダー（Headers）**
```
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Accept: application/json
```
リクエストのメタ情報を伝える。認証情報、データ形式、言語設定などが含まれる。

**3. ボディ（Body）**
```json
{
  "name": "田中太郎",
  "email": "tanaka@example.com"
}
```
POST / PUTリクエストで送信するデータ。GETリクエストには通常ボディがない。

### HTTPメソッドの使い分け

| メソッド | 用途 | ボディ | 例 |
|----------|------|--------|-----|
| GET | データの取得 | なし | ユーザー一覧の取得 |
| POST | データの新規作成 | あり | ユーザーの登録 |
| PUT | データの全体更新 | あり | ユーザー情報の更新 |
| PATCH | データの部分更新 | あり | メールアドレスのみ変更 |
| DELETE | データの削除 | なし | ユーザーの削除 |

### ステータスコードの分類

ステータスコードは3桁の数字で、最初の桁がカテゴリを示す。

**2xx — 成功**
- `200 OK`: リクエスト成功
- `201 Created`: 新しいリソースが作成された
- `204 No Content`: 成功したが返すデータがない（DELETE後など）

**4xx — クライアントエラー**
- `400 Bad Request`: リクエストの形式が不正
- `401 Unauthorized`: 認証が必要（トークンなし・期限切れ）
- `403 Forbidden`: 認証済みだが権限がない
- `404 Not Found`: リソースが存在しない
- `422 Unprocessable Entity`: データ形式は正しいがバリデーションエラー

**5xx — サーバーエラー**
- `500 Internal Server Error`: サーバー側の予期しないエラー
- `502 Bad Gateway`: 中間サーバーが不正な応答を受けた
- `503 Service Unavailable`: サーバーが一時的に利用不可

### エラーレスポンスの読み方

多くのAPIはエラー時にJSON形式で詳細情報を返す。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Email format is invalid",
    "field": "email"
  }
}
```

ステータスコードでエラーの大分類を判断し、レスポンスボディで具体的な原因を特定する。4xxならクライアント（自分の送ったリクエスト）に問題があり、5xxならサーバー側に問題がある。

## 4) 実務解釈シナリオ

### シナリオ A
- 状況: フロントエンドからユーザー登録APIを呼び出すと、`422 Unprocessable Entity`が返る。
- レスポンス:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Password must be at least 8 characters",
    "field": "password"
  }
}
```
- 解釈:
  - 422はデータの形式は正しいがバリデーションに失敗した場合に返される。
  - パスワードが8文字未満であることが原因である。
  - サーバー側の問題ではなく、クライアントが送るデータを修正すれば解決する。

### シナリオ B
- 状況: ユーザー一覧を取得するGETリクエストが`401 Unauthorized`を返す。
- レスポンスヘッダー: `WWW-Authenticate: Bearer`
- 解釈:
  - 認証トークンが送られていない、または期限が切れている。
  - Authorizationヘッダーにトークンが含まれているか確認する。
  - トークンが含まれている場合は、トークンの有効期限を確認する。
  - 403ではなく401なので、権限不足ではなく認証自体が失敗している。

## 5) よくあるミス

1. 401と403を混同する。
401は「誰なのか分からない」（認証失敗）、403は「誰かは分かるが権限がない」（認可失敗）である。

2. GETリクエストにボディを付けて送る。
仕様上は禁止されていないが、多くのサーバーやプロキシがGETのボディを無視する。パラメータはクエリストリングで渡すべきである。

3. ステータスコードを無視してレスポンスボディだけを見る。
ボディが空の場合やエラーメッセージが汎用的な場合、ステータスコードが唯一の手がかりになる。

4. 5xxエラーをクライアント側で修正しようとする。
5xxはサーバー側の問題であり、リクエストを変えても解決しない可能性が高い。

5. Content-Typeヘッダーの不一致を見落とす。
JSONを送るのに`Content-Type: application/x-www-form-urlencoded`になっていると、サーバーが正しくパースできない。

## 7) 出題抽出メモ

- 事実型候補: HTTPメソッドの用途、ステータスコードの分類と意味
- 判断型候補: ステータスコードからエラーの所在を判断する
- シナリオ型候補: 422バリデーションエラーの原因特定、401と403の区別
- 誤答誘導ポイント: 401と403の混同、GETリクエストでのボディ送信
