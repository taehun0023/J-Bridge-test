## 1) 학습 목표

- HTTP 요청의 구성 요소(메서드, 헤더, 바디)를 설명할 수 있다.
- 상태 코드(2xx / 4xx / 5xx)의 의미를 구분할 수 있다.
- API 응답에서 에러 메시지를 읽고 원인을 추론할 수 있다.
- 자주 사용되는 HTTP 메서드(GET / POST / PUT / DELETE)의 차이를 설명할 수 있다.

## 2) 업무 맥락

현대 웹 애플리케이션은 거의 모두 API를 통해 데이터를 주고받는다. 프론트엔드와 백엔드 사이, 혹은 서비스 간의 통신은 HTTP 프로토콜에 기반한다. 개발 중 "API가 동작하지 않는다"는 상황에 직면했을 때, 요청과 응답의 구조를 올바르게 읽을 수 없다면 원인 파악에 불필요한 시간을 쓰게 된다. 상태 코드의 의미만 알아도 문제의 소재(클라이언트 측인지 서버 측인지)를 즉시 판단할 수 있다.

## 3) 핵심 설명

### HTTP 요청의 구조

HTTP 요청은 세 가지 주요 부분으로 구성된다.

**1. 요청 라인**
```
GET /api/users/123 HTTP/1.1
```
메서드(GET), 경로(/api/users/123), HTTP 버전이 포함된다.

**2. 헤더(Headers)**
```
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Accept: application/json
```
요청의 메타 정보를 전달한다. 인증 정보, 데이터 형식, 언어 설정 등이 포함된다.

**3. 바디(Body)**
```json
{
  "name": "田中太郎",
  "email": "tanaka@example.com"
}
```
POST / PUT 요청에서 전송하는 데이터. GET 요청에는 보통 바디가 없다.

### HTTP 메서드의 구분

| 메서드 | 용도 | 바디 | 예시 |
|--------|------|------|------|
| GET | 데이터 조회 | 없음 | 사용자 목록 조회 |
| POST | 데이터 신규 생성 | 있음 | 사용자 등록 |
| PUT | 데이터 전체 수정 | 있음 | 사용자 정보 수정 |
| PATCH | 데이터 부분 수정 | 있음 | 이메일만 변경 |
| DELETE | 데이터 삭제 | 없음 | 사용자 삭제 |

### 상태 코드의 분류

상태 코드는 3자리 숫자로, 첫 번째 자리가 카테고리를 나타낸다.

**2xx -- 성공**
- `200 OK`: 요청 성공
- `201 Created`: 새 리소스가 생성됨
- `204 No Content`: 성공했으나 반환할 데이터가 없음 (DELETE 후 등)

**4xx -- 클라이언트 에러**
- `400 Bad Request`: 요청 형식이 잘못됨
- `401 Unauthorized`: 인증이 필요함 (토큰 없음·만료)
- `403 Forbidden`: 인증은 되었으나 권한이 없음
- `404 Not Found`: 리소스가 존재하지 않음
- `422 Unprocessable Entity`: 데이터 형식은 맞으나 유효성 검사 실패

**5xx -- 서버 에러**
- `500 Internal Server Error`: 서버 측의 예기치 않은 에러
- `502 Bad Gateway`: 중간 서버가 잘못된 응답을 받음
- `503 Service Unavailable`: 서버가 일시적으로 사용 불가

### 에러 응답 읽는 법

많은 API는 에러 시 JSON 형식으로 상세 정보를 반환한다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Email format is invalid",
    "field": "email"
  }
}
```

상태 코드로 에러의 대분류를 판단하고, 응답 바디로 구체적 원인을 파악한다. 4xx이면 클라이언트(내가 보낸 요청)에 문제가 있고, 5xx이면 서버 측에 문제가 있다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 상황: 프론트엔드에서 사용자 등록 API를 호출하면 `422 Unprocessable Entity`가 반환된다.
- 응답:
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Password must be at least 8 characters",
    "field": "password"
  }
}
```
- 해석:
  - 422는 데이터 형식은 올바르지만 유효성 검사에 실패한 경우에 반환된다.
  - 비밀번호가 8글자 미만인 것이 원인이다.
  - 서버 측 문제가 아니며, 클라이언트가 보내는 데이터를 수정하면 해결된다.

### 시나리오 B
- 상황: 사용자 목록을 조회하는 GET 요청이 `401 Unauthorized`를 반환한다.
- 응답 헤더: `WWW-Authenticate: Bearer`
- 해석:
  - 인증 토큰이 전송되지 않았거나 만료되었다.
  - Authorization 헤더에 토큰이 포함되어 있는지 확인한다.
  - 토큰이 포함되어 있다면 토큰의 유효기간을 확인한다.
  - 403이 아닌 401이므로, 권한 부족이 아니라 인증 자체가 실패한 것이다.

## 5) 자주 하는 실수

1. 401과 403을 혼동한다.
401은 "누구인지 모른다"(인증 실패), 403은 "누구인지는 알지만 권한이 없다"(인가 실패)이다.

2. GET 요청에 바디를 붙여 보낸다.
스펙상 금지는 아니지만, 많은 서버와 프록시가 GET의 바디를 무시한다. 파라미터는 쿼리 스트링으로 전달해야 한다.

3. 상태 코드를 무시하고 응답 바디만 본다.
바디가 비어있거나 에러 메시지가 범용적일 때, 상태 코드가 유일한 단서가 된다.

4. 5xx 에러를 클라이언트 측에서 수정하려 한다.
5xx는 서버 측 문제이며, 요청을 바꿔도 해결되지 않을 가능성이 높다.

5. Content-Type 헤더의 불일치를 간과한다.
JSON을 보내면서 `Content-Type: application/x-www-form-urlencoded`로 되어 있으면 서버가 올바르게 파싱할 수 없다.
