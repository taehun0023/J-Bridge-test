## 1) 学習目標

- コードレビューで確認すべき核心的な観点を説明できる。
- 建設的なレビューコメントの特徴を区別できる。
- レビューフィードバックを受けた時の適切な対応方法を説明できる。
- レビュー者とレビュイー双方の責任を理解できる。

## 2) 業務コンテキスト

コードレビューは品質管理のためだけでなく、チーム内の知識共有とスキル向上のための重要なプロセスである。しかし、何を見ればいいのか分からない状態でレビューに臨むと、表面的な指摘（命名規則やフォーマット）だけに終わったり、逆にレビューを受ける側が指摘を個人攻撃と受け取ってしまったりする。効果的なコードレビューのための観点と心構えを理解することが、チーム開発の基礎である。

## 3) 要点解説

### レビューで確認すべき観点

コードレビューで見るべきポイントは大きく5つに分類される。

**1. 正確性（Correctness）**
- コードが仕様通りに動作するか
- エッジケース（境界値、null、空配列など）は考慮されているか
- 既存の機能を壊していないか

**2. 可読性（Readability）**
- 変数名・関数名が意図を明確に伝えているか
- コメントが必要な複雑な処理にコメントがあるか
- 不要なコードやコメントアウトが残っていないか

**3. 保守性（Maintainability）**
- 重複したコードがないか
- 適切な粒度で関数やクラスに分割されているか
- 将来の変更に対して柔軟な設計か

**4. セキュリティ**
- ユーザー入力のバリデーションは行われているか
- SQLインジェクションやXSSの脆弱性はないか
- 秘密情報がコードに含まれていないか

**5. パフォーマンス**
- 不要なループやN+1クエリはないか
- 大量データへの考慮があるか

### 建設的なコメントの書き方

良いレビューコメントには以下の特徴がある。

**良い例:**
```
この条件分岐でuserがnullの場合を考慮すると、
NullPointerExceptionが発生する可能性があります。
nullチェックを追加するのはどうでしょうか？
```

**悪い例:**
```
ここおかしい。修正して。
```

建設的なコメントは3つの要素を含む。
1. **何が問題か**（事実の指摘）
2. **なぜ問題か**（理由の説明）
3. **どうすれば良いか**（改善の提案）

また、コメントの種類を明示すると効果的である。
- `[must]`: 必ず修正すべき問題
- `[nit]`: 些細な改善提案（修正しなくても承認可能）
- `[question]`: 理解のための質問

### フィードバックを受ける側の対応

レビューフィードバックを受けた時に重要なのは以下の点である。

1. **指摘をコードに対するものとして受け取る**。自分自身への批判ではない。
2. **理由が分からなければ質問する**。「なぜこの変更が必要ですか？」と聞くことは恥ずかしいことではない。
3. **合意できない場合は根拠を示して議論する**。「仰ることは理解しましたが、〇〇の理由でこのままの方が良いと考えます」と伝える。
4. **すべての指摘に対応またはコメントを返す**。無視は最悪の対応である。

## 4) 実務解釈シナリオ

### シナリオ A
- レビューコメント: 「この処理、遅くない？」
- 問題点:
  - 何が遅いのか具体的でない。
  - なぜ遅いと判断したのか根拠がない。
  - 改善提案がない。
- 改善案: 「このループ内でDBクエリが実行されており、ユーザー数がN件の場合にN回のクエリが発生します（N+1問題）。事前にバッチ取得するか、JOINで1回のクエリにまとめるのはどうでしょうか？」

### シナリオ B
- レビューコメント: 「[must] ユーザー入力を直接SQLに埋め込んでおり、SQLインジェクションのリスクがあります。プレースホルダーを使用してください。」
- 対応:
  - これはセキュリティに関わる必須修正であることが`[must]`で明確に示されている。
  - 問題（SQLインジェクション）、理由（ユーザー入力の直接埋め込み）、提案（プレースホルダー使用）が揃った良いコメントである。
  - 速やかにプレースホルダーに修正し、修正完了をコメントで返す。

## 5) よくあるミス

1. フォーマットや命名規則だけを指摘して、ロジックの正確性を確認しない。
表面的なレビューでは本質的なバグやセキュリティ問題を見逃す。

2. 個人の好みを「必須修正」として指摘する。
`[nit]`と`[must]`の区別がないと、レビュイーがすべての指摘に同じ重要度を感じてしまう。

3. レビューフィードバックを個人攻撃と受け取り、感情的に反応する。
指摘はコードに対するものであり、議論の余地があるなら根拠を示して建設的に議論する。

4. 指摘を無視して修正せずマージする。
未対応の指摘は技術的負債やバグの原因になる。

5. レビュー依頼時にPRの背景や変更意図を説明しない。
レビュー者が文脈を理解できず、的外れな指摘をしたり、レビューに時間がかかる。

## 6) 確認質問

1. コードレビューで確認すべき5つの主要な観点は何か？
2. 建設的なレビューコメントに含まれるべき3つの要素は何か？
3. `[must]`と`[nit]`の違いは何か？
4. レビューフィードバックの指摘に同意できない場合、どう対応すべきか？
5. レビュー依頼時にPRの説明文が重要な理由は何か？

## 7) 出題抽出メモ

- 事実型候補: レビュー観点の5分類、建設的コメントの構成要素
- 判断型候補: 良いコメントと悪いコメントの区別
- シナリオ型候補: 曖昧なコメントの改善、セキュリティ指摘への対応
- 誤答誘導ポイント: フォーマット指摘だけで十分と考える、フィードバックを個人攻撃と解釈する
