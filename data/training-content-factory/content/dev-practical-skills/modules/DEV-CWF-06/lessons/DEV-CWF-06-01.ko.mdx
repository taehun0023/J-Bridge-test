## 1) 학습 목표

- 코드 리뷰에서 확인해야 할 핵심 관점을 설명할 수 있다.
- 건설적인 리뷰 코멘트의 특징을 구분할 수 있다.
- 리뷰 피드백을 받았을 때 적절한 대응 방법을 설명할 수 있다.
- 리뷰어와 리뷰이 양쪽의 책임을 이해할 수 있다.

## 2) 업무 맥락

코드 리뷰는 품질 관리뿐만 아니라 팀 내 지식 공유와 스킬 향상을 위한 중요한 프로세스다. 하지만 무엇을 봐야 하는지 모르는 상태로 리뷰에 임하면 표면적 지적(네이밍 규칙이나 포맷)에만 그치거나, 반대로 리뷰를 받는 쪽이 지적을 개인 공격으로 받아들일 수 있다. 효과적인 코드 리뷰를 위한 관점과 마음가짐을 이해하는 것이 팀 개발의 기초다.

## 3) 핵심 설명

### 리뷰에서 확인할 관점

코드 리뷰에서 봐야 할 포인트는 크게 5가지로 분류된다.

**1. 정확성(Correctness)**
- 코드가 명세대로 동작하는가
- 엣지 케이스(경곗값, null, 빈 배열 등)를 고려했는가
- 기존 기능을 깨뜨리지 않는가

**2. 가독성(Readability)**
- 변수명·함수명이 의도를 명확하게 전달하는가
- 복잡한 처리에 주석이 있는가
- 불필요한 코드나 주석 처리된 코드가 남아있지 않은가

**3. 유지보수성(Maintainability)**
- 중복된 코드가 없는가
- 적절한 단위로 함수나 클래스가 분리되었는가
- 향후 변경에 유연한 설계인가

**4. 보안**
- 사용자 입력의 유효성 검사가 수행되는가
- SQL 인젝션이나 XSS 취약점이 없는가
- 비밀 정보가 코드에 포함되어 있지 않은가

**5. 성능**
- 불필요한 루프나 N+1 쿼리가 없는가
- 대량 데이터에 대한 고려가 있는가

### 건설적인 코멘트 작성법

좋은 리뷰 코멘트에는 다음의 특징이 있다.

**좋은 예:**
```
이 조건 분기에서 user가 null인 경우를 고려하면
NullPointerException이 발생할 수 있습니다.
null 체크를 추가하는 것은 어떨까요?
```

**나쁜 예:**
```
여기 이상함. 수정해.
```

건설적인 코멘트는 3가지 요소를 포함한다.
1. **무엇이 문제인가** (사실 지적)
2. **왜 문제인가** (이유 설명)
3. **어떻게 하면 좋은가** (개선 제안)

또한, 코멘트의 종류를 명시하면 효과적이다.
- `[must]`: 반드시 수정해야 하는 문제
- `[nit]`: 사소한 개선 제안 (수정 안 해도 승인 가능)
- `[question]`: 이해를 위한 질문

### 피드백을 받는 쪽의 대응

리뷰 피드백을 받았을 때 중요한 점은 다음과 같다.

1. **지적을 코드에 대한 것으로 받아들인다**. 자기 자신에 대한 비판이 아니다.
2. **이유를 모르면 질문한다**. "왜 이 변경이 필요한가요?"라고 묻는 것은 부끄러운 일이 아니다.
3. **동의할 수 없으면 근거를 들어 논의한다**. "말씀하신 점은 이해했지만, OO의 이유로 이대로가 낫다고 생각합니다"라고 전달한다.
4. **모든 지적에 대응하거나 코멘트를 남긴다**. 무시는 최악의 대응이다.

## 4) 실무 해석 시나리오

### 시나리오 A
- 리뷰 코멘트: "이 처리 느리지 않아?"
- 문제점:
  - 무엇이 느린지 구체적이지 않다.
  - 왜 느리다고 판단했는지 근거가 없다.
  - 개선 제안이 없다.
- 개선안: "이 루프 내에서 DB 쿼리가 실행되고 있어, 유저 수가 N건이면 N번의 쿼리가 발생합니다(N+1 문제). 사전에 배치 조회하거나 JOIN으로 1회 쿼리로 묶는 것은 어떨까요?"

### 시나리오 B
- 리뷰 코멘트: "[must] 사용자 입력을 직접 SQL에 삽입하고 있어 SQL 인젝션 위험이 있습니다. 플레이스홀더를 사용해 주세요."
- 대응:
  - 보안에 관련된 필수 수정임이 `[must]`로 명확히 표시되어 있다.
  - 문제(SQL 인젝션), 이유(사용자 입력 직접 삽입), 제안(플레이스홀더 사용)이 갖춰진 좋은 코멘트다.
  - 신속히 플레이스홀더로 수정하고, 수정 완료를 코멘트로 남긴다.

## 5) 자주 하는 실수

1. 포맷이나 네이밍 규칙만 지적하고 로직의 정확성을 확인하지 않는다.
표면적 리뷰로는 본질적인 버그나 보안 문제를 놓친다.

2. 개인 취향을 "필수 수정"으로 지적한다.
`[nit]`와 `[must]`의 구분이 없으면 리뷰이가 모든 지적에 같은 중요도를 느끼게 된다.

3. 리뷰 피드백을 개인 공격으로 받아들여 감정적으로 반응한다.
지적은 코드에 대한 것이며, 이견이 있다면 근거를 들어 건설적으로 논의한다.

4. 지적을 무시하고 수정 없이 머지한다.
미대응 지적은 기술 부채나 버그의 원인이 된다.

5. 리뷰 요청 시 PR의 배경이나 변경 의도를 설명하지 않는다.
리뷰어가 맥락을 이해하지 못해 엉뚱한 지적을 하거나 리뷰에 시간이 오래 걸린다.

## 6) 확인 질문

1. 코드 리뷰에서 확인해야 할 5가지 주요 관점은 무엇인가?
2. 건설적인 리뷰 코멘트에 포함되어야 할 3가지 요소는 무엇인가?
3. `[must]`와 `[nit]`의 차이는 무엇인가?
4. 리뷰 피드백의 지적에 동의할 수 없을 때 어떻게 대응해야 하는가?
5. 리뷰 요청 시 PR 설명이 중요한 이유는 무엇인가?

## 7) 문항 발췌 메모

- 사실형 후보: 리뷰 관점의 5가지 분류, 건설적 코멘트의 구성 요소
- 판단형 후보: 좋은 코멘트와 나쁜 코멘트의 구분
- 시나리오형 후보: 모호한 코멘트의 개선, 보안 지적에 대한 대응
- 오답 유도 포인트: 포맷 지적만으로 충분하다고 생각, 피드백을 개인 공격으로 해석
