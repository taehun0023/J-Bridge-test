## 1) 학습 목표

- Java의 예외 계층(Throwable → Error / Exception → RuntimeException)을 설명할 수 있다.
- checked 예외와 unchecked 예외의 차이와 각각의 처리 의무를 설명할 수 있다.
- 스택 트레이스를 읽고 예외 발생 지점과 호출 경로를 특정할 수 있다.
- try-catch-finally의 실행 순서를 정확히 추적할 수 있다.

## 2) 업무 맥락

운영 환경에서 장애가 발생하면 가장 먼저 확인하는 것이 로그에 출력된 스택 트레이스다. 스택 트레이스를 올바르게 읽을 수 있으면 장애 원인 지점을 몇 분 만에 특정할 수 있다. 반대로 읽지 못하면 코드를 한 줄씩 추적하는 비효율적 조사가 된다. 또한 checked 예외와 unchecked 예외의 차이를 이해하지 못하면 컴파일 에러 대처나 에러 핸들링 설계에서 판단을 그르친다.

## 3) 핵심 설명

### 예외 계층

Java의 예외는 모두 `Throwable`을 상속한다. 크게 2가지로 나뉜다.

- **Error**: JVM 레벨의 치명적 문제(`OutOfMemoryError` 등). 애플리케이션 코드에서 잡으면 안 된다.
- **Exception**: 애플리케이션 레벨의 예외. 다시 2가지로 나뉜다.
  - **checked 예외**(`Exception` 직계): 컴파일러가 처리를 강제한다. `IOException`, `SQLException` 등.
  - **unchecked 예외**(`RuntimeException` 계열): 컴파일러가 강제하지 않는다. `NullPointerException`, `IllegalArgumentException` 등.

```java
// checked 예외 — 호출부에서 try-catch 또는 throws 선언 필수
public String readFile(String path) throws IOException {
    return Files.readString(Path.of(path));
}

// unchecked 예외 — 선언 불요하지만 발생 가능성 있음
public int divide(int a, int b) {
    return a / b; // b==0이면 ArithmeticException
}
```

### 스택 트레이스 읽는 법

스택 트레이스는 **아래에서 위로** 읽는다. 최하단이 호출 시작점이고 최상단이 예외 발생 지점이다.

```
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()"
    at com.example.service.UserService.validateName(UserService.java:25)
    at com.example.service.UserService.createUser(UserService.java:12)
    at com.example.Main.main(Main.java:8)
```

이 경우 `Main.main()` → `UserService.createUser()` → `UserService.validateName()` 순으로 호출되어 25번째 줄에서 `NullPointerException`이 발생했다. 메시지로부터 `String.length()`를 null 객체에 호출한 것을 알 수 있다.

### try-catch-finally 실행 순서

```java
try {
    String result = riskyOperation();
    System.out.println(result);
} catch (IOException e) {
    System.out.println("IO 에러: " + e.getMessage());
} catch (Exception e) {
    System.out.println("기타 에러: " + e.getMessage());
} finally {
    System.out.println("반드시 실행됨");
}
```

catch 블록은 **위에서 아래로** 매칭된다. 구체적인 예외를 먼저, 범용 예외를 나중에 작성한다. finally 블록은 예외 유무와 관계없이 반드시 실행된다. 리소스 닫기에 자주 사용되지만 Java 7 이후에는 `try-with-resources`가 권장된다.

```java
try (var reader = new BufferedReader(new FileReader(path))) {
    return reader.readLine();
} // 자동으로 reader.close()가 호출됨
```

## 4) 실무 해석 시나리오

### 시나리오 A
```
Caused by: java.sql.SQLException: Connection refused
    at com.mysql.cj.jdbc.ConnectionImpl.createNewIO(ConnectionImpl.java:826)
    at com.example.dao.UserDao.findById(UserDao.java:34)
    at com.example.service.UserService.getUser(UserService.java:18)
```
- 읽기 포인트:
  - `Caused by`는 연쇄 예외의 근본 원인을 나타낸다.
  - `SQLException: Connection refused`로 DB 연결 문제임을 알 수 있다.
  - 애플리케이션 코드 쪽은 `UserDao.java:34`가 첫 접점이며 여기에 DB 연결 로직이 있다.

### 시나리오 B
```java
public void processOrder(Order order) {
    try {
        validate(order);
        save(order);
    } catch (ValidationException e) {
        log.warn("검증 실패: {}", e.getMessage());
        throw e; // 재throw
    } catch (Exception e) {
        log.error("예기치 않은 에러", e);
        throw new ServiceException("주문 처리 실패", e);
    }
}
```
- 해석:
  - `ValidationException`은 경고 로그를 남기고 그대로 재throw한다. 호출부가 처리하는 설계다.
  - 그 외 예외는 `ServiceException`으로 감싸서 재throw한다. 원인 예외를 `e`로 체이닝한 점이 중요하다.
  - 이 설계 덕분에 호출부는 `ServiceException`만 catch하면 된다.

## 5) 자주 하는 실수

1. catch 블록에서 범용 `Exception`을 먼저 작성한다.
`catch (Exception e)`를 먼저 쓰면 모든 예외가 거기서 잡혀 구체적인 catch 블록에 도달하지 않는다.

2. 스택 트레이스를 위에서만 읽는다.
`Caused by` 섹션에 근본 원인이 있는 것을 놓친다.

3. checked 예외를 catch로 삼켜버린다.
빈 catch 블록(`catch (Exception e) {}`)은 버그 원인을 은폐하는 최악의 패턴이다.

4. finally 블록에서 return 문을 작성한다.
try 블록의 반환값을 finally의 return이 덮어써 예상 밖의 반환값이 된다.

5. 예외 메시지에 사용자 입력을 포함할 때의 보안 위험.
스택 트레이스가 로그에 출력되므로 비밀번호 등 민감 정보를 예외 메시지에 포함하면 안 된다.
