# 제네릭스의 기초 -- 타입 파라미터와 타입 안전

## 1) 요점 정리 (5줄)

- **타입 파라미터 `<T>`** 를 클래스나 메서드에 선언함으로써, 컴파일 시에 타입 안전을 보장할 수 있다 (Evidence: E2)
- **타입 소거(Type Erasure)** 에 의해, 제네릭스의 타입 정보는 컴파일 후 소거되어 실행 시에는 구별되지 않는다 (Evidence: E3)
- **raw type**을 사용하면 타입 안전이 상실되어, 실행 시에 `ClassCastException`이 발생할 위험이 있다 (Evidence: E1, E4)
- 타입 파라미터에는 **참조 타입만** 지정 가능하며, 프리미티브 타입은 사용할 수 없다. 래퍼 타입을 사용한다 (Evidence: E7)
- **다이아몬드 연산자 `<>`** 에 의해, 우변의 타입 파라미터를 컴파일러가 추론해준다 (Evidence: E6)

## 2) 개념

### 제네릭스 도입 전의 문제

Java 5 이전의 컬렉션은 `Object` 타입으로 요소를 저장했다. 꺼낼 때 캐스트가 필요하며, 타입을 잘못 지정하면 실행 시에 `ClassCastException`이 발생했다 (Evidence: E1). 이 문제는 컴파일 시에 검출할 수 없어, 버그 발견이 늦어지는 원인이 되었다.

### 타입 파라미터 `<T>`

제네릭스에서는 클래스나 인터페이스에 타입 파라미터를 선언하여, 컴파일 시에 타입 안전을 보장한다 (Evidence: E2).

```java
public class Box<T> {
    private T value;

    public Box(T value) { this.value = value; }
    public T getValue() { return value; }
}
```

`Box<String>`이라고 기술하면, `String` 이외의 타입을 저장하려 하면 컴파일 에러가 된다. 꺼낼 때 캐스트도 불필요해진다.

### 타입 파라미터의 명명 관례

타입 파라미터에는 관례적으로 다음의 1문자가 사용된다 (Evidence: E8).

| 파라미터 | 의미 |
|---|---|
| `T` | Type (범용 타입) |
| `E` | Element (컬렉션 요소) |
| `K` | Key (맵의 키) |
| `V` | Value (맵의 값) |
| `N` | Number (숫자) |

### 타입 소거 (Type Erasure)

컴파일 후, 제네릭스의 타입 정보는 소거된다 (Evidence: E3). 실행 시에는 `Box<String>`과 `Box<Integer>`는 같은 `Box` 클래스로 취급된다. 이를 통해 후방 호환성은 유지되지만, 실행 시에 타입 파라미터를 가져올 수는 없다.

### raw type의 위험성

타입 파라미터를 생략한 raw type(예: `Box box = new Box();`)을 사용하면, 컴파일러가 경고를 내고 타입 안전이 상실된다 (Evidence: E4). 기존 코드와의 호환성을 위해 허용되지만, 새로운 코드에서는 사용해서는 안 된다.

### 제네릭스 메서드

메서드 단위로 타입 파라미터를 선언하는 것도 가능하다. 타입 파라미터는 메서드의 리턴 타입 앞에 기술한다 (Evidence: E5).

```java
public static <T> T firstOrNull(List<T> list) {
    return list.isEmpty() ? null : list.get(0);
}
```

이 형태를 사용하면, 클래스 전체를 제네릭스화하지 않아도 특정 메서드만 타입 안전하게 만들 수 있다.

### 다이아몬드 연산자 `<>`

Java 7 이후, 우변의 타입 파라미터를 컴파일러가 추론하는 다이아몬드 연산자를 사용할 수 있다 (Evidence: E6).

```java
// Java 7 이전
Box<String> box = new Box<String>("hello");

// Java 7 이후 — 다이아몬드 연산자
Box<String> box = new Box<>("hello");
```

### 복수 타입 파라미터

클래스나 인터페이스에 복수의 타입 파라미터를 정의할 수 있다 (Evidence: E11).

```java
public interface Pair<K, V> {
    K getKey();
    V getValue();
}
```

## 3) 예제 (2개)

### 예제 1: 제네릭스 미사용 -- Object 캐스트 + ClassCastException

제네릭스를 사용하지 않는 경우, `Object` 타입으로 저장되므로 꺼낼 때 타입을 잘못 지정하면 실행 시 오류가 발생한다 (Evidence: E1).

```java
import java.util.ArrayList;
import java.util.List;

public class WithoutGenerics {
    public static void main(String[] args) {
        // raw type의 List — 무엇이든 저장할 수 있어 버림
        List list = new ArrayList();
        list.add("hello");
        list.add(42);  // 컴파일 에러가 되지 않는다!

        // 꺼낼 때 캐스트가 필요
        String s = (String) list.get(0);  // OK
        String t = (String) list.get(1);  // ClassCastException!
    }
}
```

이 코드는 컴파일은 통과하지만, `list.get(1)` 줄에서 `Integer`를 `String`으로 캐스트하려 하여 `ClassCastException`이 발생한다. 문제는 실행하기 전까지 버그를 발견할 수 없다는 점이다.

### 예제 2: 제네릭스 사용 -- 컴파일 시 타입 안전

제네릭스를 사용하면 타입 불일치를 컴파일 시에 검출할 수 있다 (Evidence: E2).

```java
import java.util.ArrayList;
import java.util.List;

public class WithGenerics {
    public static void main(String[] args) {
        // 제네릭스 첨부 List — String만 저장 가능
        List<String> list = new ArrayList<>();  // 다이아몬드 연산자 (Evidence: E6)
        list.add("hello");
        // list.add(42);  // 컴파일 에러! 타입 안전이 보장됨

        // 꺼낼 때 캐스트 불필요
        String s = list.get(0);  // 안전하게 가져옴

        // 제네릭스 메서드 사용 예 (Evidence: E5)
        String first = firstOrNull(list);
        System.out.println(first);  // "hello"
    }

    public static <T> T firstOrNull(List<T> list) {
        return list.isEmpty() ? null : list.get(0);
    }
}
```

타입 파라미터에 의해, 저장과 꺼내기의 타입이 일치함이 컴파일 시에 보장된다. 캐스트 불필요로 안전한 코드가 된다.

## 4) 흔한 실수 / 함정 (5개)

### 1. raw type 사용

```java
// NG: raw type — 타입 안전이 상실됨
Box box = new Box("hello");  // 컴파일러 경고 발생

// OK: 타입 파라미터를 지정
Box<String> box = new Box<>("hello");
```

raw type은 제네릭스의 타입 체크를 무효화한다. 기존 pre-Java 5 코드와의 호환성을 위해서만 존재하며, 새로운 코드에서는 사용하지 말 것 (Evidence: E4).

### 2. 프리미티브 타입 지정

```java
// NG: 프리미티브 타입은 컴파일 에러
Box<int> box = new Box<>(42);

// OK: 래퍼 타입을 사용
Box<Integer> box = new Box<>(42);  // 오토박싱
```

타입 파라미터에는 참조 타입만 지정 가능하다. 프리미티브 타입을 사용하고 싶은 경우 래퍼 타입을 사용한다 (Evidence: E7).

### 3. 제네릭스 배열의 직접 생성

```java
// NG: 컴파일 에러 — 제네릭스 배열은 생성 불가
Box<String>[] boxes = new Box<String>[10];
T[] array = new T[10];

// OK: Collection을 사용하거나 와일드카드로 회피
List<Box<String>> boxes = new ArrayList<>();
```

타입 소거에 의해 실행 시 타입 파라미터 정보가 사라지므로, 타입 안전을 보장할 수 없어 컴파일러가 제네릭스 배열의 직접 생성을 금지한다 (Evidence: E10).

### 4. instanceof에서의 제네릭스 타입 사용

```java
// NG: 컴파일 에러
if (obj instanceof Box<String>) { ... }

// OK: 비경계 와일드카드 (Box<?>)로 판정한 후 캐스트
if (obj instanceof Box<?>) { ... }
```

타입 소거에 의해 실행 시 타입 파라미터 정보가 존재하지 않으므로, `instanceof`에서 제네릭스 타입을 직접 지정할 수 없다 (Evidence: E9). 와일드카드 `<?>`는 사용 가능.

### 5. 타입 파라미터 추론에 지나치게 의존

```java
// 모호한 경우, 컴파일러가 Object로 추론할 가능성
var result = firstOrNull(List.of());  // T가 Object가 됨

// 타입을 명시
String result = GenericUtil.<String>firstOrNull(List.of());
```

다이아몬드 연산자나 메서드의 타입 추론은 편리하지만, 인수가 비어 있거나 `null`인 경우 의도하지 않은 타입으로 추론될 수 있다. 필요에 따라 타입을 명시할 것.

## 5) 체크리스트

학습 후, 다음 항목을 확인하자.

- [ ] 제네릭스를 사용하지 않는 코드에서 `ClassCastException`이 발생하는 케이스를 설명할 수 있다
- [ ] `<T>`를 사용한 제네릭스 클래스를 스스로 정의할 수 있다
- [ ] 타입 소거(Type Erasure)의 구조와 그 영향을 설명할 수 있다
- [ ] raw type을 사용해서는 안 되는 이유를 설명할 수 있다
- [ ] 제네릭스 메서드의 구문(리턴 타입 앞에 `<T>`를 선언)을 작성할 수 있다
- [ ] 다이아몬드 연산자 `<>`가 어떻게 타입 추론하는지 설명할 수 있다
- [ ] 프리미티브 타입이 타입 파라미터에 사용할 수 없는 이유를 설명할 수 있다
- [ ] 제네릭스 배열을 직접 생성할 수 없는 이유를 설명할 수 있다
- [ ] `instanceof`에 제네릭스 타입을 사용할 수 없는 이유를 설명할 수 있다
- [ ] 복수 타입 파라미터를 가진 클래스/인터페이스를 정의할 수 있다
