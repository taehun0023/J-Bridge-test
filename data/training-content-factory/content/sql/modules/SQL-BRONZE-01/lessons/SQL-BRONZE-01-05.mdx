## 1) 要点まとめ（5行）

- **JOIN** は複数のテーブルを結合条件に基づいて 1 つの結果セットにまとめる SQL の機能である。
- **INNER JOIN** は両テーブルで条件に一致する行のみ返す。一致しない行は結果に含まれない。
- **LEFT JOIN** は左テーブルの全行を返し、右テーブルに一致がなければ NULL で埋める。
- **ON** 句で結合条件（通常は主キーと外部キーの等値比較）を指定する。
- テーブル別名（alias）を使うと、複数テーブルの列を簡潔に参照でき、クエリの可読性が向上する。

## 2) 概念

### なぜ JOIN が必要なのか

✅ 結論: リレーショナルデータベースではデータを複数テーブルに正規化して格納するため、JOIN で関連データを結合して取得する必要がある。

リレーショナルデータベース設計では、データの重複を避けるためにテーブルを分割する（正規化）。例えば、社員テーブルに部署名を直接持たず、部署テーブルを別に作成し、`department_id` で関連付ける。

```
employees テーブル         departments テーブル
+----+--------+----+      +----+--------+--------+
| id | name   |d_id|      | id | name   |location|
+----+--------+----+      +----+--------+--------+
|  1 | 田中   |  1 |      |  1 | 開発部 | 東京   |
|  2 | 佐藤   |  2 |      |  2 | 営業部 | 大阪   |
|  3 | 鈴木   |  1 |      |  3 | 人事部 | 東京   |
+----+--------+----+      +----+--------+--------+
```

「田中さんはどの部署？」を知るには、両テーブルを `department_id` で結合する必要がある。

### JOIN の基本構文

✅ 結論: JOIN は FROM 句の中でテーブル同士を結合し、ON 句で結合条件を指定する。

```sql
SELECT 列名
FROM テーブルA
JOIN テーブルB ON テーブルA.列 = テーブルB.列;
```

### INNER JOIN — 一致する行のみ

✅ 結論: INNER JOIN は両テーブルで結合条件を満たす行の組み合わせのみ返す。

```sql
SELECT e.name, d.name AS department_name
FROM employees e
INNER JOIN departments d ON e.department_id = d.id;
```

| name | department_name |
|---|---|
| 田中太郎 | 開発部 |
| 佐藤花子 | 営業部 |
| 鈴木一郎 | 開発部 |

INNER JOIN の動作を図で示す:

```
employees                departments
+------+------+          +------+------+
| 田中 | d=1  |---+  +---| id=1 | 開発 |
| 佐藤 | d=2  |---+--+---| id=2 | 営業 |
| 鈴木 | d=1  |---+  |   | id=3 | 人事 |
| 木村 | d=99 |  (不一致) +------+------+
+------+------+

結果: 田中-開発, 佐藤-営業, 鈴木-開発
(木村は d=99 に一致する部署がないので除外)
(人事部は所属社員がいないので除外)
```

`INNER` キーワードは省略可能であり、`JOIN` だけでも INNER JOIN と同じ動作をする。

```sql
-- 以下は同じ
SELECT e.name, d.name FROM employees e JOIN departments d ON e.department_id = d.id;
SELECT e.name, d.name FROM employees e INNER JOIN departments d ON e.department_id = d.id;
```

### LEFT JOIN — 左テーブルを基準に結合

✅ 結論: LEFT JOIN は左テーブルの全行を必ず返し、右テーブルに一致がない場合は NULL で埋める。

```sql
SELECT e.name, d.name AS department_name
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id;
```

| name | department_name |
|---|---|
| 田中太郎 | 開発部 |
| 佐藤花子 | 営業部 |
| 鈴木一郎 | 開発部 |
| 木村五郎 | NULL |

LEFT JOIN の動作を図で示す:

```
employees (左)           departments (右)
+------+------+          +------+------+
| 田中 | d=1  |--------->| id=1 | 開発 |  ✓
| 佐藤 | d=2  |--------->| id=2 | 営業 |  ✓
| 鈴木 | d=1  |--------->| id=1 | 開発 |  ✓
| 木村 | d=99 |--> NULL  | id=3 | 人事 |
+------+------+          +------+------+

結果: 田中-開発, 佐藤-営業, 鈴木-開発, 木村-NULL
(木村は右テーブルに一致なし → NULL で埋める)
```

`LEFT JOIN` は正式には `LEFT OUTER JOIN` と書く。`OUTER` は省略可能。

### LEFT JOIN で不一致データを抽出する

✅ 結論: LEFT JOIN + WHERE 右テーブル IS NULL で「左にあって右にないデータ」を抽出できる。

```sql
-- 有効な部署に所属していない社員を見つける
SELECT e.name, e.department_id
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id
WHERE d.id IS NULL;
```

| name | department_id |
|---|---|
| 木村五郎 | 99 |

このパターンは「孤立データ」の検出に非常に便利で、データ品質チェックに頻繁に使われる。

### テーブル別名（alias）

✅ 結論: テーブル別名を使うとクエリが簡潔になり、同名列の曖昧性を解消できる。

```sql
-- AS あり（省略可能）
SELECT e.name, d.name AS department_name
FROM employees AS e
INNER JOIN departments AS d ON e.department_id = d.id;

-- AS 省略
SELECT e.name, d.name AS department_name
FROM employees e
INNER JOIN departments d ON e.department_id = d.id;
```

テーブル別名を使う理由:
1. **簡潔さ**: `employees.name` より `e.name` の方が短い。
2. **曖昧性の解消**: 両テーブルに `name` 列がある場合、`e.name` と `d.name` で区別する。
3. **必須の場合**: 同じテーブルを 2 回結合する場合（自己結合）。

同名列を別名なしで参照すると「曖昧な列参照」エラーが発生する。

```sql
-- NG: name が employees にも departments にもあるため曖昧
SELECT name FROM employees e JOIN departments d ON e.department_id = d.id;

-- OK: テーブル別名で修飾
SELECT e.name FROM employees e JOIN departments d ON e.department_id = d.id;
```

### 3 テーブル以上の結合

✅ 結論: JOIN を連鎖的に記述することで、3 つ以上のテーブルを結合できる。

```sql
SELECT
    e.name       AS employee_name,
    d.name       AS department_name,
    p.name       AS project_name,
    pa.role      AS project_role
FROM employees e
INNER JOIN departments d ON e.department_id = d.id
INNER JOIN project_assignments pa ON e.id = pa.employee_id
INNER JOIN projects p ON pa.project_id = p.id;
```

| employee_name | department_name | project_name | project_role |
|---|---|---|---|
| 田中太郎 | 開発部 | Webリニューアル | リーダー |
| 鈴木一郎 | 開発部 | Webリニューアル | メンバー |
| 佐藤花子 | 営業部 | 営業支援システム | メンバー |

この例では 4 つのテーブル（employees, departments, project_assignments, projects）を結合している。`project_assignments` は社員とプロジェクトの多対多の関係を管理する中間テーブルである。

### INNER JOIN と LEFT JOIN の使い分け

| 状況 | 推奨 JOIN |
|---|---|
| 両方にデータがある行だけ必要 | INNER JOIN |
| 左テーブルの全行を保持したい | LEFT JOIN |
| 不一致（孤立）データを見つけたい | LEFT JOIN + WHERE IS NULL |

RIGHT JOIN は LEFT JOIN の左右を入れ替えたものと等価だが、実務では LEFT JOIN に統一する慣習が広く普及している。

## 3) 例（2つ）

### 例1: 社員とその部署情報を取得する（一致なしも含む）

```sql
SELECT
    e.id,
    e.name       AS employee_name,
    e.salary,
    d.name       AS department_name,
    d.location
FROM employees e
LEFT JOIN departments d ON e.department_id = d.id
ORDER BY e.id;
```

| id | employee_name | salary | department_name | location |
|---|---|---|---|---|
| 1 | 田中太郎 | 450000 | 開発部 | 東京 |
| 2 | 佐藤花子 | 380000 | 営業部 | 大阪 |
| 3 | 鈴木一郎 | 520000 | 開発部 | 東京 |
| 4 | 木村五郎 | 300000 | NULL | NULL |

LEFT JOIN を使うことで、有効な部署に所属していない木村五郎も結果に含まれる。INNER JOIN の場合は木村五郎が除外される。

### 例2: 社員のプロジェクト参加状況を確認する

```sql
SELECT
    e.name       AS employee_name,
    p.name       AS project_name,
    pa.role
FROM employees e
LEFT JOIN project_assignments pa ON e.id = pa.employee_id
LEFT JOIN projects p ON pa.project_id = p.id
ORDER BY e.name;
```

| employee_name | project_name | role |
|---|---|---|
| 佐藤花子 | 営業支援システム | メンバー |
| 鈴木一郎 | Webリニューアル | メンバー |
| 田中太郎 | Webリニューアル | リーダー |
| 木村五郎 | NULL | NULL |

LEFT JOIN を 2 回使うことで、プロジェクトに参加していない木村五郎も結果に含まれる。

## 4) よくあるミス／落とし穴（5つ）

⚠️ **ミス1**: ON 句の結合条件を間違えてクロス結合になる → **対策**: ON 句には必ず正しい主キー/外部キーの等値条件を書く。ON を忘れると構文エラーまたはクロス結合（全行の組み合わせ）になる。

⚠️ **ミス2**: INNER JOIN と LEFT JOIN を混同する → **対策**: 「一致データだけ必要か」「左テーブルの全行が必要か」で使い分ける。

⚠️ **ミス3**: 同名列をテーブル名で修飾しない → **対策**: JOIN 使用時は全ての列をテーブル別名で修飾する習慣を付ける。

⚠️ **ミス4**: LEFT JOIN の後の WHERE で右テーブルの列を条件にして INNER JOIN 相当になる → **対策**: 右テーブルの条件は ON 句に含めるか、IS NULL チェックを意図している場合のみ WHERE に書く。

⚠️ **ミス5**: 結合を増やしすぎてクエリが複雑になる → **対策**: テーブルを 4 つ以上結合する場合は、サブクエリや WITH 句（CTE）を検討する。
