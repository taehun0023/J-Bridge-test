## 1) 요점 정리 (5줄)

- **SELECT** 절에서 가져올 열을 지정하고, **FROM** 절에서 데이터 소스가 되는 테이블을 지정한다.
- `SELECT *`는 전체 열 조회의 축약 표기이지만, 실무 코드에서는 열 이름을 명시적으로 작성하는 것이 권장된다.
- **AS** 키워드로 열에 별칭(alias)을 부여하면, 결과 세트의 헤더가 알기 쉬워진다.
- **DISTINCT**는 SELECT 바로 뒤에 배치하여, 결과 세트에서 중복 행을 제거한다.
- SQL 키워드는 대소문자를 구분하지 않지만, 대문자로 작성하는 관례가 널리 사용되고 있다.

## 2) 개념

### SELECT 문의 기본 구조

✅ 결론: SQL에서 데이터를 가져오려면, 최소한 `SELECT`와 `FROM` 두 개의 절이 필요하다.

SQL(Structured Query Language)은 관계형 데이터베이스를 조작하기 위한 표준 언어이다. 데이터를 "조회"(쿼리)할 때 가장 기본이 되는 것이 SELECT 문이다.

```sql
SELECT 열이름1, 열이름2, ...
FROM 테이블이름;
```

이 구문은 "어떤 테이블에서(FROM), 어떤 열을(SELECT) 가져올 것인가"를 선언적으로 기술한다. SQL은 프로그래밍 언어처럼 "절차"를 작성하는 것이 아니라, "무엇을 원하는가"를 기술하는 선언형 언어이다.

| 절 | 역할 | 필수 |
|---|---|---|
| SELECT | 가져올 열을 지정 | 예 |
| FROM | 데이터 소스 테이블을 지정 | 예 |

### 전체 열 조회 (SELECT *)

✅ 결론: `SELECT *`는 간편하지만, 운영 환경에서는 필요한 열만 지정해야 한다.

```sql
SELECT * FROM employees;
```

`*`(애스터리스크)는 "테이블의 전체 열"을 의미한다. 개발 중 탐색이나 디버깅에는 편리하지만, 다음과 같은 이유로 실무 코드에서는 피해야 한다.

1. 테이블에 열이 추가되면, 예상하지 못한 데이터가 반환된다.
2. 불필요한 열의 데이터 전송으로 성능이 저하된다.
3. 코드의 가독성이 떨어지고, 어떤 열을 사용하는지 파악하기 어렵다.

### 열 지정

✅ 결론: 필요한 열만 쉼표로 구분하여 지정하면, 효율적이고 유지보수하기 쉬운 쿼리가 된다.

```sql
SELECT name, salary, hire_date
FROM employees;
```

SELECT 절에는 쉼표(,)로 구분하여 여러 열을 나열할 수 있다. 열의 순서는 테이블 정의의 순서와 일치할 필요가 없으며, 자유롭게 지정할 수 있다.

### 열 별칭 (AS)

✅ 결론: AS로 열에 알기 쉬운 별칭을 부여하면, 결과 세트의 가독성이 향상된다.

```sql
SELECT name AS 사원명, salary AS 월급
FROM employees;
```

AS 키워드는 생략 가능하며, 다음과 같이 작성할 수도 있다.

```sql
SELECT name 사원명, salary 월급
FROM employees;
```

다만, 가독성 관점에서 AS를 명시하는 것이 권장된다. 별칭에 공백이나 예약어를 포함할 경우에는 이중 따옴표로 감싸야 한다.

```sql
SELECT name AS "Employee Name"
FROM employees;
```

| 표기법 | 예 | 비고 |
|---|---|---|
| AS 있음 | `salary AS monthly_pay` | 권장 |
| AS 생략 | `salary monthly_pay` | 생략 가능 |
| 이중 따옴표 | `salary AS "Monthly Pay"` | 공백을 포함하는 경우 |

### DISTINCT — 중복 행 제거

✅ 결론: DISTINCT는 SELECT 절에서 지정한 모든 열의 조합에 대해 중복 판정을 수행하고, 고유한 행만 반환한다.

```sql
SELECT DISTINCT department_id
FROM employees;
```

DISTINCT는 SELECT 바로 뒤에 한 번만 기술한다. 여러 열을 지정한 경우에는, 해당 전체 열 값의 "조합"으로 중복을 판정한다.

```sql
-- department_id와 salary의 조합으로 중복 판정
SELECT DISTINCT department_id, salary
FROM employees;
```

DISTINCT는 내부적으로 정렬이나 해시 처리를 수행하므로, 대량 데이터에 대해서는 성능 비용이 있다는 점에 유의해야 한다.

### SQL 문 작성 관례

SQL 키워드(SELECT, FROM, AS, DISTINCT 등)는 대소문자를 구분하지 않는다. 아래는 모두 같은 결과를 반환한다.

```sql
SELECT name FROM employees;
select name from employees;
Select Name From Employees;
```

다만, 업계 관례로서 "키워드는 대문자, 테이블명/열명은 소문자"로 작성하는 경우가 많다. 또한, 문장 끝에는 세미콜론(`;`)을 붙이는 것이 표준이다.

## 3) 예제 (2개)

### 예제 1: 사원의 이름과 급여를 별칭 포함으로 조회하기

```sql
SELECT
    name   AS employee_name,
    salary AS monthly_salary
FROM employees;
```

| employee_name | monthly_salary |
|---|---|
| 田中太郎 | 450000 |
| 佐藤花子 | 380000 |
| 鈴木一郎 | 520000 |

이 예제에서는 `name` 열에 `employee_name`, `salary` 열에 `monthly_salary`라는 별칭을 부여하고 있다. 원래 테이블의 스키마는 변경되지 않으며, 결과 세트의 표시 이름만 바뀐다.

### 예제 2: 부서 ID 목록을 중복 없이 조회하기

```sql
SELECT DISTINCT department_id
FROM employees;
```

| department_id |
|---|
| 1 |
| 2 |
| 3 |

사원 테이블에는 여러 사원이 같은 부서에 소속되어 있지만, DISTINCT를 사용하면 부서 ID 목록을 고유하게 조회할 수 있다. 부서 테이블이 없는 상황에서도, 어떤 부서가 존재하는지 조사할 때 유용한 기법이다.

## 4) 흔한 실수 / 함정 (5개)

⚠️ **실수 1**: `SELECT * FROM`을 실무 코드에서 사용 → **대책**: 필요한 열 이름을 명시적으로 나열한다. 테이블 변경 시 영향 범위가 명확해진다.

⚠️ **실수 2**: 열 별칭에 공백을 포함하는데 따옴표를 붙이지 않음 → **대책**: `AS "Column Name"`과 같이 이중 따옴표로 감싼다.

⚠️ **실수 3**: DISTINCT를 열마다 작성하려고 함 (`SELECT DISTINCT name, DISTINCT salary`) → **대책**: DISTINCT는 SELECT 바로 뒤에 한 번만 기술한다. 모든 열의 조합에 적용된다.

⚠️ **실수 4**: SQL 문 끝에 세미콜론을 빠뜨림 → **대책**: 습관적으로 세미콜론을 반드시 붙인다. 여러 문을 실행할 때는 필수이다.

⚠️ **실수 5**: 대량 데이터에 의미 없이 DISTINCT를 붙임 → **대책**: 정말로 중복 제거가 필요한지 확인한 후 사용한다. 불필요한 DISTINCT는 성능을 저하시킨다.
