## 1) 학습 목표
- HTTP 메서드와 상태 코드의 분류를 이해하고 구분하여 사용할 수 있다
- DNS 이름 해석의 흐름을 순서대로 설명할 수 있다
- 일반적인 네트워크 장애의 원인을 특정하고 기본적인 진단을 할 수 있다

## 2) 왜 중요한가
HTTP와 DNS는 인터넷의 기반 기술이며, 웹 애플리케이션 개발자가 매일 접하는 프로토콜이다. 상태 코드를 정확히 이해하지 못하면 API의 오류 처리가 부적절해지고, DNS의 구조를 모르면 장애 시 원인 파악이 어려워진다. 운영 및 유지보수 현장에서 즉시 활약하기 위해 반드시 필요한 지식이다.

## 3) 핵심 설명
- **HTTP 메서드**: GET(조회), POST(생성), PUT(전체 수정), PATCH(부분 수정), DELETE(삭제)가 기본이다. RESTful API 설계에서는 리소스 조작과 메서드를 일치시키는 것이 원칙이다
- **상태 코드**: 2xx(성공), 3xx(리다이렉트), 4xx(클라이언트 오류), 5xx(서버 오류)의 4가지로 분류된다. 특히 200, 201, 301, 400, 401, 403, 404, 500, 502, 503은 자주 등장한다
- **DNS 이름 해석**: 브라우저가 도메인 이름에서 IP 주소를 얻는 구조이다. 로컬 캐시 → 재귀 리졸버 → 루트 DNS → TLD DNS → 권위 DNS 순서로 조회한다

## 4) 작동 방식 또는 판단 흐름
1. **DNS 해석 흐름**: 사용자가 URL 입력 → 브라우저 캐시 확인 → OS 캐시 확인 → 재귀 리졸버에 문의 → 루트 DNS에서 TLD, 권위 DNS로 추적하여 IP 주소 취득 → 결과를 캐시하여 TTL 동안 유지
2. **HTTP 요청과 응답**: 클라이언트가 메서드, 헤더, 본문을 포함한 요청을 전송 → 서버가 처리 후 상태 코드, 헤더, 본문을 반환한다. 상태 코드의 첫째 자리로 성공 여부를 즉시 판단할 수 있다
3. **장애 진단 기본 절차**: 먼저 ping으로 통신 확인 → traceroute로 경로 확인 → nslookup으로 DNS 해석 확인 → curl로 HTTP 응답 확인. 문제의 계층(물리, DNS, 애플리케이션)을 분리하여 파악한다

## 5) 비슷한 개념과의 비교
- **301 vs 302**: 301은 영구 리다이렉트(SEO 평가가 이전 대상에 계승됨), 302는 임시 리다이렉트이다. 용도를 혼동하면 SEO나 캐시에 악영향을 줄 수 있다
- **401 vs 403**: 401은 인증 미완료(로그인이 필요), 403은 인가 거부(로그인은 되었지만 권한이 없음)이다. 보안 설계에서 올바르게 구분해야 한다

## 6) 자주 하는 오해
- "404는 서버가 다운되었다는 뜻이다" → 404는 리소스를 찾을 수 없을 뿐이며 서버 자체는 정상 동작하고 있다. 서버 장애는 5xx로 표현된다
- "DNS는 한 번 설정하면 즉시 반영된다" → DNS 전파에는 TTL에 따른 시간이 걸린다. 변경 후 전 세계 캐시가 업데이트되기까지 수 분에서 수 시간이 소요될 수 있다
- "GET 요청에 본문을 포함해도 괜찮다" → HTTP 사양상 금지는 아니지만 많은 서버와 프록시가 GET의 본문을 무시하거나 거부한다. 실무에서는 피해야 한다

## 7) 확인 질문
1. HTTP 상태 코드 401과 403의 차이를 설명하세요
2. DNS 이름 해석에서 브라우저가 IP 주소를 얻기까지의 흐름을 순서대로 설명하세요
3. "502 Bad Gateway"가 발생하는 대표적인 원인은 무엇인가요
4. 웹사이트에 접속할 수 없을 때 원인을 파악하기 위해 어떤 순서로 진단하나요

## 8) 문항 추출 메모
- 상태 코드의 의미와 분류(2xx/3xx/4xx/5xx)는 객관식 문제의 단골 주제이다
- DNS 해석 순서(캐시 → 리졸버 → 루트 → TLD → 권위)는 순서 문제에 최적이다
- 장애 시나리오(ping은 되지만 HTTP 실패, DNS 해석 불가 등)는 시나리오 문제로 출제할 수 있다
